## One `llama-server` runs as a system service and sleeps when idle

Decision: a single `llama-server` runs under systemd as a dedicated system user, bound to `127.0.0.1` on a fixed port, the model given as `-hf <repo>:<quant> --offline` with `LLAMA_CACHE=/data2/llama.cpp`, and `--sleep-idle-seconds` set so that the weights and KV cache leave the GPUs after a period without requests and come back on the next one. Every user of `cpd` reaches it; opencode's provider for all of them points at it.

**Narrowed as built, 2026-11-04.** The unit exists but runs `User=edjulien`, stays `disable`d at boot and is started on demand, and it is restricted to one card by `CUDA_VISIBLE_DEVICES=0`. The system user, the cache ACLs and the shared provider all moved to the as-built note's `Deferred` list, on the ground that `edjulien` is the only opencode user on `cpd` today, so the account and its permissions would be work with no consumer. What survives of the reasoning: the ownership argument that rejected a `tmux` session still holds the day a second user appears, and the recon of 2026-11-04 showed no `llama-server` running under any user, so nothing had claimed that lifecycle in the meantime. What changed in kind: with the unit disabled and started by hand, `systemctl stop` became the real way to free the card and `--sleep-idle-seconds` the secondary one, inverting the roles this section gave them.

Why: the server is shared, so its lifecycle cannot belong to any one user's account. `--sleep-idle-seconds` exists at tag `b9286` (`tools/server/README.md`, section "Sleeping on Idle", read through `gh api` on 2026-09-24: "the model and its associated memory (including the KV cache) are unloaded"), and it removes the objection that condemned a systemd unit on `ju-TP2` in `DESIGN-GPU-REMOTE.md`, section "One command on `ju-TP` owns both ends of a session, as a script in `bin`", where the unit would have held 4.3 GiB of VRAM permanently. That earlier decision stands for `ju-TP2`: a single user, an SSH-split topology and no sleep mode considered.

Referent: `_meta/backup/.config/systemd/user/backup-cpd000001.service`, the repository's existing systemd unit concerning `cpd`; beyond it, systemd is the Ubuntu idiom for a shared daemon, and sleep-on-idle is llama.cpp's own answer to VRAM held by an idle server.

What it trades: a server that wakes while other users have filled the GPUs fails to reload, and opencode then receives an error. A process administered through `systemctl`, restarted on failure and logged to the journal is what that buys.

Weakest assumption, **confirmed 2026-11-04** by `_meta/cpd/trial-check.sh` (log `_meta/cpd/cpd-trial-20261104-155909.log`): sleep does free VRAM under CUDA, `is_sleeping` going `true` after 75 s without a request with the cards at 188 MiB each, then 7602, 7814 and 8998 MiB once the next request wakes the model. The log holds no loaded reading taken before that sleep: the check script's `vram while loaded` probe sat before any chat request, so it read 186 MiB. The likeliest reading of that figure is a server already idled out between its launch and the start of the checks, but the log does not establish it: the delay between the two is nowhere recorded, and 186 MiB is only known to be far below a loaded 27B. The conclusion therefore rests on the sleeping state and the post-wake state, both observed, rather than on a before-and-after pair. Fixed 2026-11-05 after a verifier pass found it: that first probe is relabelled as taken before any request, and a second one reads the VRAM right after the first reply, so the next run produces the pair this one lacks. It does not free everything: those 188 MiB per card, about 0.55 GiB in all, are the CUDA context the sleeping server keeps, against a 1 MiB floor before any launch. The loaded figure from that log is 24414 MiB across three cards, about 23.8 GiB, for weights plus a 98304-token KV cache; the as-built note records 24458 MiB for the same shape from the user's own run, so the two differ by a run rather than by a reading. `-hf … --offline` also resolves the cached model, `model_path` coming back as the snapshot path under `/data2/llama.cpp`, so the `--model` fallback stays unused. Both were measured under `edjulien` rather than a service user, which is the one part of the assumption still open.

Rejected:

- **An adapted `llama-session` in local mode**, the first user starting the server and the next ones reusing it. The process belongs to whoever started it: when that user leaves or interrupts it the others lose the server, and nobody else can stop or restart it. The sleep mode already gives the one thing it offered, VRAM released when unused.
- **`llama-session` or a bare `llama-server` held in a `tmux` session**, the user's first idea. It is the same ownership as above, with no restart after a crash or a reboot and logs only in the pane's scrollback. It stays the right way to try the launch command in the foreground before writing the unit, which the tutorial does.
- **One server per user.** N copies of about 16 GiB of weights on three shared cards, and port collisions.
- **Router mode** (`--models-preset`), which serves several models on demand: nothing asks for a second model. It sits on top of the same service the day one is wanted.

## llama.cpp is updated to b11065 beside b9286, through `llama-update`

**Superseded 2026-11-04 and kept as record**, the heading included: no build was installed on `cpd`. The two sections that follow hold why it was decided and why it was dropped, and the research below on Turing coverage and on the release archives is what a future install would start from.

- **`eds-avc` stays on b9286.** `LLAMA_BIN_DIR` points off the PATH, so the name `llama-server` keeps resolving to b9286. Switching an ongoing model comparison to another inference engine is an analysis decision, left to the user.

Rejected: a source build for sm_75, which `/usr/local` or an admin would own and which `llama-update` cannot roll back; the manual `curl` and `tar` of the two archives, which loses the gate and the rollback for no gain; `LLAMA_BIN_DIR=/usr/local/bin`, which would move `eds-avc` onto b11065 behind its back.

Untested: the first-start JIT time on Turing, and whether `llama-update` run through `sudo env` behaves as under the user account; running it against scratch paths from `ju-TP` was refused on 2026-09-24, so its overrides are checked by reading the script only.

## The `/data2` build is b9286 and lacks only `--reasoning-effort`, 2026-11-04

Measured by `_meta/cpd/recon.sh`: the binary at `/data2/llama_cpp_bin/llama.cpp/build/bin/llama-server` answers `version: 9286 (99d4026b1)`, built 2026-08-14, and belongs to another user (mode 775, inside a `/data2/llama_cpp_bin` that same user owns). It is therefore the very build `eds-avc` calls, not a recent one, and the user's decision to keep it was taken believing otherwise. Its 17920 bytes are explained: `ldd` shows a shared-library build, `libllama-server-impl.so`, `libllama.so.0` and a `libggml-cuda.so.0` of 138 MB sitting beside it, CUDA linked through `libcudart.so.12` and `libcublas.so.12`.

Of the six options the parameters rest on, five are present in the raw help: `--reasoning`, `--sleep-idle-seconds`, `--no-mmproj`, `--jinja` and `--offline`, alongside `--hf-repo`, `--ctx-size`, `--parallel`, `--alias`, `-ngl` and `-m`. The one genuine absence is `--reasoning-effort`, which the raw help confirms by what it does carry instead: `--reasoning-format`, `-rea, --reasoning [on|off|auto]`, `--reasoning-budget` and `--reasoning-budget-message`. That single absence matches this note's own research ("b9286 lacks `--reasoning-effort`"), while the `--offline` it attributed to b11065 turns out to exist at b9286 too.

**The probe reported six of those as absent, and was wrong on all six.** Both committed recon logs name `--offline`, `--hf-repo`, `--ctx-size`, `-hf`, `-ngl` and `-m` as not found, and the raw help dumped in the second log carries every one of them. The test was `printf '%s' "$help" | grep -qE …` under `set -Eeuo pipefail`: `grep -q` exits 0 on its first match, `printf` then dies of SIGPIPE at 141, and `pipefail` makes that the pipeline's status, so a match was read as a miss. The fault is a race on whether `grep` exits before `printf` finishes writing 51231 bytes. Position correlates without determining: all six misses sit between lines 26 and 198 of a 640-line help, while every option matching later was reported correctly, and yet `-c`, on the very same line as `--ctx-size`, came back present. That counterexample is what rules out a deterministic cause and leaves the race.

The fix is a here-string, `grep -qE … <<<"$help"`, which has no pipeline and so no race. Replayed on the logged bytes, the old form reproduces the misses with `pipefail` on and loses them with it off, and the new form gives the same six present over five consecutive runs. **Those replays are unlogged**, run here against the logged help text: both committed logs predate the fix, so no log on `cpd` shows the corrected verdict, and the option list this section states rests on the raw help dump rather than on any probe output. The same shape sat in the candidate-ports test and is fixed there too, though those results happened to be right, that list being short enough to finish writing first. This is the failure mode `feedback_shell_grep_pipefail` already records, written into a probe whose whole purpose was to be trusted over a slow link.

What the single absence costs: the deferred thinking A/B of "Parameters" cannot be run, `--reasoning-effort` being its whole mechanism. Nothing else. The procedure's steps 5 and 6 and the unit's `ExecStart` work as written, `--hf-repo … --offline` included, so the `--model` fallback stays unused, and `--sleep-idle-seconds` survives, which keeps the assumption that justified a permanent service over a per-user process.

**The trial settles it in favour of b9286, 2026-11-04.** `_meta/cpd/trial-check.sh` ran the procedure's step 5 against it and every requirement held: the model loads, the chat template is accepted, `--reasoning off` and the non-thinking sampler both reach the server, tool calls work, and the idle sleep returns the VRAM. The template concern that justified a recent build did not materialise, so keeping b9286 costs only the thinking A/B of "Parameters", which was already deferred. One objection stands and is not answered by any measurement: the binary belongs to another user, so a rebuild or a deletion on their side breaks the service with no notice. The escape hatch if that happens is the b11065 route of the superseded section above, with its step 3 restored, and nothing in the procedure forecloses it.

`_meta/cpd/trial-serve.sh` and `_meta/cpd/trial-check.sh` carry that load attempt, split because it occupies two terminals: the first runs the procedure's step 5 command in the foreground, the second runs step 5's checks and logs them for the hand-back. Six values are environment overrides on what the recon established, the binary, the cache, the port, the repo, the quant and the idle seconds, `CPD_PORT` defaulting to 8090 and `CPD_MODEL_QUANT` to `UD-Q4_K_M`; the rest is hard-coded, `--alias`, `--ctx-size 98304`, `-ngl 99`, `--parallel` and the sampler flags included, so a change there is an edit rather than a variable. The serve script refuses before launching on two conditions, a binary that is not executable and a port already listening, the second read through a here-string for the reason the section above gives. What the check script decides, in order: whether the template loads at all, which is the open question; whether `--reasoning off` takes effect, read as a `reasoning_content` of length 0; whether tool calls work, without which opencode is unusable; and whether the idle sleep actually returns the VRAM, which is this design's weakest assumption.

## opencode is the upstream binary, its provider declared once in `/etc/opencode`

- Binary: the release archive `opencode-linux-x64.tar.gz` (v1.18.32 on 2026-09-24, asset list read through `gh api`; downloaded that day, it holds the single executable `opencode`, linked against glibc alone) extracted into `/usr/local/bin`. The `@ai-sdk/openai-compatible` provider is bundled in the binary: `ju-TP` holds no downloaded copy of it anywhere under `~/.config/opencode`, `~/.cache/opencode` or `~/.local/share/opencode`, so users without plugins need no npm registry. It needs no Node for other users, which the npm route of `ju-TP` (`DESIGN-GPU-REMOTE.md` step 4) would; that route was chosen there for `sys-update` coverage, which `cpd` does not have. The CPU has AVX2, so the `baseline` variant is not needed.
- Provider: `/etc/opencode/opencode.json`, the managed configuration directory opencode documents for Linux (opencode.ai/docs/config, read 2026-09-24), highest in its precedence list. It holds the provider and `model` only, so that it imposes nothing else on the other users.

**Both halves were overtaken as built, 2026-11-04.** opencode 1.19.5 sits in `~/.opencode/bin` under the user's own account rather than `/usr/local/bin`, and `/etc/opencode` is empty: the single tracked `opencode.json` was repointed at the `cpd` provider instead (`71ff1ec`). Both the system-wide binary and the managed provider sit on the as-built note's `Deferred` list with the rest of the multi-user shape.

Weakest assumption, **never tested, and not under test**: that the managed file merges with a user's `~/.config/opencode/opencode.json`, its `model` winning and the user's `permission`, `instructions` and `skills` surviving. It becomes live the day two machines serve at once or a second user appears on `cpd`, and `opencode debug config` is what checks it in one line. The v2 documentation read on 2026-11-04 keeps `/etc/opencode` as the system directory with the highest precedence, so the lever is the documented one and did not go away.

Version, measured 2026-11-04: the newest release is `v2.2.5` (2026-10-30), and it does carry the CLI, `opencode-linux-x64.tar.gz` being among its assets. Both stable channels still name 1.19.5 all the same, `repos/anomalyco/opencode/releases/latest` returning `v1.19.5` and the npm dist-tag `latest` of `opencode-ai` resolving to `1.19.5`, with no 2.x published for that package. The v2 line is therefore released without being flagged as the default install.

**The v2 config schema breaks the stowed file, and the plugin has no 2.x.** On `opencode.ai/v2/docs/config/`, read 2026-11-04, `permission` becomes `permissions` and turns from an object into an array of rules, and `provider` becomes `providers`; neither singular appears on the page, and no migration guide exists anywhere under `/v2/docs/`. `@opencode-ai/plugin`, which opencode installs from npm at first start for `plugins/claude-hooks.ts`, publishes no 2.x either (dist-tag `latest` 1.19.5). So a v2 on `cpd` would mean rewriting in the v2 schema the hundred-entry permission block that is the harness's security surface, unguided, on the one machine where iteration costs a manual round trip. What does survive v2 is the lever this section rests on: `/etc/opencode` is still the system directory, still highest precedence, still merged key by key. What does not is `OPENCODE_CONFIG`, absent from the v2 page, so it is a v1-only fallback.

**Both halves of that paragraph were overtaken by the migration, 2026-11-11.** V2 reads a V1 configuration through a compatibility layer and normalizes it in memory, so the hundred-entry block did not have to be rewritten unguided; the conversion is step 5 of `DESIGN-OPENCODE-HARNESS.md` § "The harness migrates to opencode V2, decided 2026-11-11" and starts from what `opencode debug config` prints. The plugin package exists as `@opencode/plugin`, published at 2.2.7 alongside the binary, and the ported plugin does not depend on it at runtime at all (same note, § "The ported plugin carries no runtime dependency, 2026-11-11"). `OPENCODE_CONFIG` is indeed gone, measured on 2.2.7: it is ignored outright, and a configuration variant is now probed with `XDG_CONFIG_HOME` and `--standalone` together.

## The user's harness comes from a clone of the public dotfiles

Scope decided by the user on 2026-09-24: the most complete harness possible without what is specific to Claude Code, which will never be installed on `cpd`.

`hebstr/dotfiles` is public on GitHub (checked 2026-09-24), so `cpd` pulls its existing clone (or clones it if absent) and stows `opencode`, `claude` and `bin` for the user's account alone. That brings `AGENTS.md`, `plugins/claude-hooks.ts` and the hook scripts it calls, `~/.claude/rules/`, the memory store, the skills of `~/.claude/skills`, and `prose-lint`. The plugin skills stay out: `skills.paths` names a link farm that does not exist there. The tracked `opencode.json` is left unchanged: the managed `model` overrides `ju-tp2/qwen3.5-9b`, and the `ju-tp2` provider stays declared and unreachable. `llama-session` and `sys-update` land on the PATH through `bin` and are not to be run on `cpd`; `llama-update` is run there by its clone path, before any stow. Other users get bare opencode plus the managed provider, with opencode's default permissions, which let the shell run unasked.

**Three of those sentences were superseded as built, 2026-11-04.** The `agents` package is stowed too, so `~/.agents/skills` is part of the harness there. `llama-update` is never run on `cpd`, no build being installed. And the tracked `opencode.json` was not left unchanged: it was repointed at `cpd` (`71ff1ec`, `d7b04c8`), which the two paragraphs below take up. What still holds: `llama-session` and `sys-update` are still not to be run there.

**The plugin skills no longer stay out, decided 2026-11-08 through `/design` and approved the same day.** The sentence "The plugin skills stay out: `skills.paths` names a link farm that does not exist there" is superseded for the seven skills of `hebstr/skills`, which is the set the user cares about on this machine: `cpd` gains a clone of that public repository at `~/Documents/packages/skills`, and the stowed `opencode.json` gains two `skills.paths` entries naming the clone's `audit` and `workflow` directories, after the farm entry, plus an `external_directory` allow on the clone. That configuration half shipped in `8047880` and reaches `cpd` by the dotfiles pull; the clone itself is still to be created there, so the seven do not load on that machine yet. Nothing else changes: `opencode-skills-sync` is untouched and still unused here, the farm directory stays empty and its entry stays declared, and the third-party plugin skills of the Claude Code cache remain out, since nothing on `cpd` can produce them. The reasoning, the measurements of 2026-11-08 on `ju-TP` and the four rejected routes are in `DESIGN-OPENCODE-HARNESS.md` § "The seven skills of `hebstr/skills` leave the farm for the clone, 2026-11-08"; this section carries the consequence for `cpd` alone. The skills clone takes the same posture as the dotfiles clone, consumer only and kept current by `git pull --ff-only`, so the bullet "The clone is a consumer, never a place the repository is edited" of "Open points" now covers two clones.

Two dependencies the harness brings that bare opencode does not: both hook scripts parse their payload with `jq`, and the plugin's `@opencode-ai/plugin` dependency is installed by opencode from the npm registry on first start (`~/.config/opencode/package.json` on `ju-TP`). Without the registry the plugin does not load; the tutorial checks for it.
The second half ends with the V2 port of 2026-11-11: the ported plugin imports its type only, so nothing is fetched from npm and the registry is no longer a condition for it to load. The `jq` dependency stands.

Merge of the managed file, per opencode.ai/docs/config read 2026-09-24: "Configuration files are merged together, not replaced", later locations overriding "only for conflicting keys", managed files highest. So the managed `model` wins over the tracked `ju-tp2/qwen3.5-9b` and the user's `permission`, `instructions` and `skills` survive; the tutorial confirms it with `opencode debug config`.

**The packages are not forked per machine, measured 2026-11-04.** The user asked whether an `opencode-ju` and an `opencode-cpd` should split, the `hf` against `--hf-repo` difference being the reason given; that difference lives in `llama-session`, which the table above already keeps off `cpd`, so it bears on no file of the `opencode` package. What is machine-specific there is three keys of `opencode.json`, `model`, `provider` and `skills.paths`, against an `instructions` list and a permission block of about a hundred entries that are not; that block is the security surface and it moved twice after this note was written (`df43109`, `1d81e36`), which is precisely where two copies would drift. `AGENTS.md` holds nothing machine-specific, `ju-tp`, `llama`, `hf`, `nvidia` and `cpd` matching none of its 134 lines. The `agents` package is upstream skill copies under `~/.agents/skills` with their lock file, and opencode discovers that root natively rather than through `skills.paths`: `prek`, `typst` and `developing-with-streamlit` appear in `opencode debug skill` on `ju-TP` beside `design` and `zotero` from `~/.claude/skills`. The one thing a fork would have bought, a config without the absent link farm, costs nothing to leave in: pointed at a directory that does not exist, `opencode debug skill` exits 0, writes nothing on stderr and still resolves 29 skills against the 66 the farm adds, so `cpd` gets those 29 and the `deny` and `ask` entries naming plugin skills go inert.

**The cost of that choice came due the same day, and it was not the cost this paragraph priced.** The reasoning above assumed the machine-specific three keys would stay on `cpd` in the managed `/etc/opencode` file. As built they were written into the shared tracked file instead (`71ff1ec` repointing `model`, `provider` and `baseURL` at `cpd`, `d7b04c8` lowering `limit.context` to 65536), so the one file both machines stow now describes `cpd` alone. On `ju-TP` that leaves a declared `baseURL` of port 8090 against `llama-session`'s default 8080, a model id naming a 27B the 9B service does not serve, and a context limit sized for the other machine; `_meta/notes/opencode-harness-setup.md` carries the detail beside the check whose expected output it invalidated. Nothing broke in practice, opencode not having run on `ju-TP` since 2026-09-25 per `.claude/DEFERRED.md`, which is why this surfaced as a stale assertion rather than as a failure.

**Resolved 2026-11-05, and resolved by the premise falling away rather than by either remedy.** The managed `/etc/opencode` route was chosen first, the tracked file reverted to its `ju-TP` values and `cpd`'s three keys written for the system directory. The user then stated that opencode will not be used against `ju-TP2` until further notice, which removes the second consumer: with nothing for `ju-TP` to point at, one stowed file naming `cpd` describes the only setup that runs, and the cost this paragraph was about stops existing. So the file keeps the `cpd` keys and gains back the `ju-tp2` provider beside them, declared and unused with its own limit, so that the day `ju-TP2` returns only `model` changes. The fork stays rejected for the reasons above; the managed route stays the answer the day two machines serve at once, and `_meta/notes/opencode-cpd-setup.md`, "Where the machine-specific keys live", holds that reasoning where a reader of the setup will meet it.

## Open points

What the build closed is in `git log` and in the as-built note, and is not repeated here. What still binds:

- **Whether a managed `/etc/opencode` file wins the merge against a stowed one**, never tested and not currently needed: it decides the multi-machine and multi-user shapes both, and `opencode debug config` answers it in one command. The fallback if it loses is a real `~/.config/opencode/opencode.json` on the machine concerned instead of a stow link.
- **Machine-specific rules text describes `ju-TP` and reaches `cpd` through the clone**: since `environment.md` and its tool inventory were deleted on 2026-09-26, it sits in `rules/install.md`, `rules/chromium.md` and `rules/python.md` ("Interpreters on this machine"), so a model reading them there gets `ju-TP`'s paths and pitfalls.
