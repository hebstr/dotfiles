On 2026-09-23 a `/workflow:reco` research then a `/cadrer` pass settled agent read access to the Zotero library (Zotero 10.0.3, `~/Zotero`, 295 PDFs, Better BibTeX).
Decision: no MCP server. A `zotero` skill in `claude/.claude/skills/` gives agents `curl` GET recipes against the local API (`localhost:23119/api/users/0/...`) and `rg` recipes over `~/Zotero/storage/*/.zotero-ft-cache`. The pref `extensions.zotero.httpServer.localAPI.enabled` goes to `true` in the `zotero` stow package's `user.js`, and `permissions.deny` blocks Better BibTeX JSON-RPC. This reverses the provisional Zoteus choice made the same day.
Usages in scope: find a reference and its citation key, search full text and quote a passage, get a PDF path for `rules/pdf.md`. Litrev export is out for now (user, 2026-09-23); annotations and notes have no content to serve.
The local API pref is set in `user.js` since 2026-09-23, and the four needed GET routes answered without a key that day (search `q`, `parentItem` plus `links.enclosure` file path, `/fulltext`, `data.citationKey` equal to the Better BibTeX key); a keyless `DELETE` got `428`. In place since 2026-09-23: the `zotero` skill (`claude/.claude/skills/zotero/SKILL.md`, model-invocable) and `Bash(curl *better-bibtex/json-rpc*)` in `permissions.deny`, tested as denied, plus its opencode counterpart in `permission.bash` of `opencode.json`, just before `"*>*": "ask"` (resolved by `opencode debug config`, no live refusal observed). No `allow` rule for the GETs: a Bash `*` matches any text, so it would auto-approve a curl that also uploads a file elsewhere, and the skill feeds agents third-party full text. Practical tests done 2026-09-23 (five fresh `claude -p` sessions, note section "Tests pratiques du skill (2026-09-23)"): all five passed, the skill loaded from its description as the first call each time, no write, no SQLite, no JSON-RPC; the description needs no change. That triggering was measured with the global memory index injected, whose line for this file names the skill. Under opencode 1.18.32 with Qwen3.5-9B (same day, three `opencode run` passes, one naming Zotero explicitly), the skill never loaded although opencode lists it and the `skill` tool is enabled. Cause not established, description unchanged (the Zotero-naming variant failed too, and the same description triggered 5/5 under Claude Code); candidates are the run being outside any git repo (the same 9B loaded a skill on 2026-09-21 from a throwaway repo), the memory index absent there, and the global opencode `AGENTS.md` line telling the model to ignore "Skill"; no write, SQLite or JSON-RPC attempt, but no final answer either, each pass ending at its first auto-rejected permission. There, read-only rests on permissions and Zotero's lock alone. Not observed yet: a live refusal under opencode. Read citation keys from `data.citationKey`, never from the `citekeyFormat` formula: a key can be pinned by hand and a formula change does not regenerate existing keys. The formula was Better BibTeX's default `auth.lower + shorttitle(3,3) + year` from 2026-09-23, restored in `user.js` at the user's request after they had briefly changed it by hand to `auth.lower + year`; since 2026-09-29 `user.js` carries `auth + "_" + year` instead, on the eds-prise decision recorded in that repository's `.claude/DESIGN-BIB.md`, so the older keys and the newer ones follow two different formulas and reading `data.citationKey` matters more than ever. See [[reference_zotero_user_js_pref_precedence]].
Research, decision, rejected options and sources: `~/dotfiles/_meta/notes/zotero-agent-access-reco.md`, section "Les agents passent par un skill et l'API locale, sans serveur MCP".
**The JSON-RPC deny rule was re-examined on 2026-09-28 at the user's prompting and kept.** The blanket phrase "exposes side-effecting methods" is replaced in the skill and the note by the inventory read in the source: fourteen methods, of which three write, `item.regenerate_key` (calls `KeyManager.fill(..., { replace: true })`, so it overwrites pinned citation keys), `autoexport.add` (parameters `collection`, `translator`, `path`, `displayOptions`, `replace`, so a persistent write to an arbitrary path, rewritten on every library change) and `collection.scanAUX`; `viewer.viewPDF` has a UI side effect, the remaining ten read. The endpoint takes GET and POST in `application/json`, with `permitBookmarklet = false` as its only origin guard and no token; both deny rules match the endpoint, not a method list, so they cover all three writers without change. Most read methods duplicate local API GETs; `item.export` and `item.pandoc_filter` are the two without an equivalent, the local API refusing Better BibTeX translator names ([[reference_better_bibtex_export_control]]). The deciding argument is that what they would fetch is a file: once a `Keep updated` auto-export is armed it lands in the repo and `cat` reads it, so the need closes by itself and no wrapper script is worth writing. The asymmetry that keeps the rule: local API writes are locked by Zotero (`428` without a granted key) while the three JSON-RPC writers are locked by nothing, and the skill feeds agents third-party full text, an injection vector that today has no write primitive within reach. **What bounds "locked by nothing", measured 2026-09-28**: `ss -ltnp | rg 23119` gives `LISTEN 127.0.0.1:23119` held by `zotero-bin`, loopback only, so the unauthenticated endpoint is reachable by a local process and not over the network. The risk is local, not remote, and neither deny rule needs changing for it.

**Granting a local-API write key was raised by the user on 2026-09-28 and refused.** The two locks do not overlap: a local-API key unlocks item and collection writes and deletes, not `item.regenerate_key` or `autoexport.add`, which live in the JSON-RPC and are gated only by the deny rule. What decides the refusal is the want of scoping, not the gravity: the need covered sixteen notices of one collection, and whether a key can be restricted to a collection is unverified, as is whether a `DELETE` trashes or purges, both in the note's "Non vérifié" register. Measured alongside: 315 top-level items all carrying a citation key, a sync account with `sync.autoSync` at its default `true` so a deletion propagates to the server, and no trustworthy local snapshot, hence the deferred library backup in the 2026-09-28 row of the dotfiles `.claude/DEFERRED.md`.

**Why:** agents have Bash, so an MCP read-only switch adds nothing: the real write lock is Zotero refusing local API writes until the user grants a key. A skill is versioned in dotfiles and also reaches opencode, which keeps MCP servers out (`.claude/DESIGN-OPENCODE-HARNESS.md`, 2026-09-21). Zotero 10 runs `zotero.sqlite` in WAL under a hardcoded exclusive lock, so direct SQLite reads while Zotero runs are locked, stale or racy.

**How to apply:** if the subject returns, read the note rather than rerun the research or the framing. If a needed API route fails, reopen the framing on that usage instead of switching to an MCP server, which would use the same API. Never grant a local API write key to an agent, and read SQLite only with Zotero closed, in `mode=ro` without `immutable`.
