When reviewing personal shell installers (e.g. `quarto-update`, `positron-update`, `rv-update`) under `~/dotfiles/bin/.local/bin/`, do NOT raise the following finding patterns:

- Defensive branching to distinguish "first install" / "parse failure" / "normal" cases on a single-user workstation where the tool is already installed
- Supply-chain concerns about checksums served from the same origin as the binary, when the upstream vendor publishes no detached signature (TLS is the only available trust root, note as informational only, no code change possible)
- Non-TTY safety (progress bar control characters, log redirection) for installers that are interactive-only by design and have no cron/systemd usage
- `sudo -v` ticket expiration during long downloads; sudo default timeout (15 min) >> typical download time, reprompt is acceptable UX even if it fired
- Cosmetic header tweaks (e.g. adding `Accept: application/vnd.github+json`) when the existing API call already returns the expected payload
- Implicit dependency prechecks for tools already provisioned in the deployment baseline (`curl`, `jq`, coreutils): confirmed present on both workstation and target servers
- GitHub API unauthenticated-rate-limit concerns for manually-invoked scripts (a few invocations/month per user, 60 req/h is never approached)
- TOCTOU between checksum verify and `sudo dpkg -i` when the work directory is `mktemp -d` (mode 0700, user-owned): no cross-user attack surface
- Vendor-CDN URL-structure fragility (e.g. `${CDN}/deb/${arch}/...` path assumption) when `curl -f` already produces a loud 404 on schema change; fail-bruyant is acceptable
- Fail-fast ordering preferences (e.g. "move the arch check before the network call") when the reviewer themselves acknowledge no correctness consequence; cosmetic fail-order is not a required fix
- Redundant explicit error handling (`|| { echo ...; exit 1; }`) for commands already covered by `set -euo pipefail` (the pipeline failure mode is already handled; the explicit handler adds noise, not safety)
- Sudo credential keepalive loops to prevent mid-run re-prompts (rare-case mitigation; one extra prompt is acceptable UX)
- Cross-distro fallback guards (e.g. `command -v apt-get` on a script that is Ubuntu-targeted and tested as such); bats tests asserting the absence of a guard are tested intent, not a bug
- Speculative parent-process / self-replace concerns (e.g. "what if `claude update` is invoked from inside `claude`") with no concrete trigger or reproducer
- Cosmetic future-proofing (column widths, separator alignment) where the failure mode is *visible misalignment* on the next run: the author sees it and fixes it in place, no silent corruption
- Stylistic refactors with no behavioral change (associative-array idioms vs. nested loops on n≤20, table-driven dispatch vs. 17 explicit handlers, status-string enums on fields with no programmatic consumer)
- Swapping `(cd "$DIR" && cmd)` for an equivalent `--prefix`/`-C`-style flag on internal-consistency grounds: the subshell `cd` is the house idiom (`anki-update`, `quarto-update`), and the flag's config-resolution semantics differ subtly enough that the trade is not free
- Rejecting a self-healing transient state: a non-exact pin (`^3.9.6`) makes `css-toolchain-update` print `↑ prettier ^3.9.6 → 3.9.6` plus a spurious drift note, but the install path's `--save-exact` rewrites the pin to exact, and `sys-update` takes that path. Hard-rejecting a malformed pin would refuse to run a script that fixes the state on its own
- In `sys-cleanup`, a sweep "deleting live cache metadata" when the owning tool regenerates that metadata on its own: rv recreates `CACHEDIR.TAG` on every `DiskCache::new()`, re-fetches `packages.mp` once `packages_timeout` (3600 s) expires, and rebuilds `builtin-<ver>.mp` locally. Check the tool's source for regeneration before raising it, the mirror image of [[feedback_verify_native_gc_semantics]] (walkthrough 2026-09-13)
- In `sys-cleanup`, an unguarded call to an optional dependency that aborts the rest of the run under `set -e` when the dependency is installed by default and the failure is loud (`pak::cache_clean()` with no pak check: `rig add` installs pak unless `--without-pak`). `sys-cleanup` runs on the workstation only, not on the multi-user servers of the "Threat model on the multi-user servers" section below, so absent-dependency triggers borrowed from that server context do not apply to it (walkthrough 2026-09-13)
- A claim that deleting a uv tool directory by hand leaves "uv's tool registry out of step": uv keeps no registry beside `~/.local/share/uv/tools/<tool>/uv-receipt.toml`, so `uv tool list` simply stops listing it. The residue is real but is not a registry: dangling `~/.local/bin` entry-point symlinks, which nothing detects, since `symlinks-check` only reports links whose target is under `~/dotfiles/` and `sys-orphans` `check_scripts` skips dangling links (`[[ -f ]]` is false). The real defects in that shape are duplicate findings, a remedy that silently uninstalls a tool still in use, and that uncovered residue. A remedy for a uv tool whose interpreter is gone must be `uv tool install --force <tool>`: `uv tool upgrade` refuses a broken environment (uv `upgrade.rs`, issue #11534), and a reinstall by name drops the extras and `--with` recorded in `uv-receipt.toml` (`sys-orphans` walkthrough, 2026-09-13). The uncovered residue stays NOTED rather than fixed, re-measured 2026-10-12 at zero occurrences: 0 dangling links across all three `BIN_DIRS`, 5 uv tool directories against 5 resolving entry points, and the two removals that could have left residue left none: `youtube-transcript-api`, which `295b5cf` dropped on 2026-08-11 from the then-live `README.md` tool list and from [[reference_tool_update_routines]], and `ouroboros-ai` in `f27d592` on 2026-10-08. How either was removed is recorded nowhere, so the zero reading rests on that measurement rather than on a clean `uv tool uninstall`, which no commit, note or transcript attests. Reopen on a real incident, per [[feedback_review_severity_heuristic_code]]; the patch site, pinned so the fix is ready, is `check_scripts` handling `-L` with `! -e` ahead of the `[[ -f ]]` test that currently swallows the case three lines before the `uv-receipt.toml` branch
- An `apt-get update` added inside a personal installer "for a fresh machine" when the documented bootstrap already runs it before the script can exist there: `_meta/notes/wsl-init-tuto.md` makes `sudo apt update` mandatory in §1, while `bin/.local/bin/` scripts only reach the PATH through `stow` in §5, and an index left stale fails loudly (`404 Not Found` per the note, "Unable to locate package" when empty). Check the bootstrap order in the setup note before raising it (`fira-code-install` walkthrough, 2026-09-14)
- Precedence between two non-zero exit codes (e.g. "exit 2 on a missing file hides the violations already printed, should exit 1") on a script whose automation consumers never read the value: `prose-lint`'s callers are `prose-lint-pretool.sh` (`if OUTPUT=$(prose-lint ...)`, zero vs non-zero) and prek (existing files only), where both codes block, and `format-on-edit.sh`, which pipes to `tail` without `pipefail` and so discards the status altogether, so the distinction is read by nobody. Read the consumers' branch on the status before raising it; a consumer that does branch on the value puts it back in scope (`prose-lint` walkthrough, 2026-09-16)
- In `prose-lint`, the inline-code masking (`gsub(/`[^`]*`/, "")`) failing on a double-backtick span that carries inner backticks, so the span leaks into the dash checks and the write is blocked. Real, met once between 2026-07-28 and 2026-10-12, and avoided three ways: a fenced block, which the masking handles and which reads better, the `<!-- prose-lint:ignore -->` marker the script already offers, and rewording. The remedy means a second alternation on the gate that filters every markdown write on this machine, where POSIX ERE has no lazy quantifier, and its mis-write direction is the dangerous one, over-masking letting a real em dash pass in silence. Dropped from the backlog 2026-10-12, L1 agreeing. Re-raise only with a case the three escapes do not cover
- A missing `command -v syncthing` guard on `sys-update`'s `update_syncthing`, or a first-install path in `syncthing-update` (misleading "keeping the installed key" wording when no keyring exists yet). The app-presence guard of `positron`/`anki`/`libreoffice`/`zotero` exists to keep desktop apps off WSL, and Syncthing is wanted on every machine: WSL receives the dotfiles themselves through it (`_meta/notes/wsl-init-tuto.md`, § Conventions: « Les dotfiles arrivent par Syncthing en réception seule »), and §4 installs it by hand, key included, before `stow bin` can put `syncthing-update` on the PATH. On any machine where the script runs, Syncthing and its keyring already exist (`sys-update` walkthrough, 2026-09-18). The exemption rests on that precondition and does not carry over by analogy: `zotero-update` is run directly for its first install, so the same wording there was a real defect, fixed by exiting 1 when the key fetch fails and no keyring exists (`zotero-update` walkthrough, 2026-09-23)
- In `win-cleanup`, an unelevated `du` on `/mnt/c/Windows/Temp` "probably reading 0 because a standard user cannot list the folder": DrvFs exposes it as `drwxrwxrwx`, and over `ssh ju-TP2` on 2026-09-19 `du -sb` returned 5252698 with exit 0 and `ls -A` listed its files. Only the elevated batch needs elevation, the measurement from WSL does not (`win-cleanup` walkthrough, 2026-09-19)
- In `win-cleanup`, the unquoted script path passed to `Start-Process -ArgumentList` breaking on a Windows user name with a space or an apostrophe: the only machine running it, `ju-TP2`, has `%LOCALAPPDATA%` at `C:\Users\julien\AppData\Local` (recorded in `.claude/DESIGN-WINDOWS.md`), so the trigger does not exist (`win-cleanup` walkthrough, 2026-09-19)

- An over-broad `require` loop called a needless hard dependency, when the tools it demands are socle on the deployment surface: `word-render` requires `pdftoppm` and `pdfinfo` in `--capture` mode, which touches neither, but poppler-utils is apt-installed and is the toolchain of both `rules/pdf.md` and `rules/docx.md`, so the refusal has no trigger, and splitting the loop per mode adds exactly the defensive branching the head of this section excludes (`word-render` walkthrough, 2026-10-04)

- A state file proposed so that a recovery path "has the value without guessing", when the caller already obtains it by live query: `word-render-payload.ps1` was asked to write its Word PID to the job directory for the case where the scheduled task's 15 min `ExecutionTimeLimit` kills it before the `finally` runs, but the driver gives up first at `TIMEOUT=240` and its timeout branch prints `task_report`, which runs `Get-Process WINWORD` on the host and lists PID, session and start time, then names the `Stop-Process -Id <pid> -Force` to run. A file written earlier is the only one of the copies that can be stale. Check what the caller's failure branch already prints before accepting a state file (`word-render-payload.ps1` walkthrough, 2026-10-04)

- `ReadOnly = $true` on the payload's `Documents.Open`, proposed because the staged copy is held writable and only `Saved = $true` plus `Close(0)` keeps Word from writing it. Both alleged harms are void: Word writes its autorecover copy to its configured autorecover location (`Options.DefaultFilePath(wdAutoRecoverPath)`, `%APPDATA%\Microsoft\Word` by default) and never beside the document, and the `~$` owner file is an ordinary file the driver's `rm -rf` of the job directory removes, resisting only while a live Word holds it, which the PID-scoped teardown ends. What remains is a cost: the tables-of-contents and fields updates modify document content, which a read-only Word refuses, so the change risks the render for no residual benefit. Re-raise only with the read-only form measured to update fields on that host (`word-render-payload.ps1` walkthrough, 2026-10-04)

- Anchoring `word-render`'s `guard_ignored` on the document's repository rather than on the output directory. The guard refuses to write captures onto git-tracked ground that the repository does not ignore, resolving its root from the target and walking up to its nearest existing ancestor, since it runs before the `mkdir -p` and `git -C` fails on a path that does not exist yet. The enumeration that decided it: of the five cases (default output, `--out-dir` in the document's repository, in another repository, outside any repository, document outside any repository), the change adds a refusal in two and removes one in none. Do not re-propose the anchor form on "an explicit `--out-dir` is the user's choice": the tool already refuses one inside the document's own repository, so that argument condemns the old form rather than the new (`word-render` suite walkthrough, 2026-10-04)

- SSH connection multiplexing (`ControlMaster`/`ControlPath`/`ControlPersist`) proposed to cut the handshake count of a low-frequency poll (one probe every 2 s during a model load) once the script already tolerates a failed probe: the socket to name, clean up and orphan on `SIGKILL` costs more than the sub-second handshakes it saves. Its correctness half, a dropped connection read as a result, is in scope and is fixed by telling ssh's exit 255 apart, not by multiplexing (`llama-session` walkthrough, 2026-09-21)

- In `transcribe`, the device and thread constants following locality rather than the host (`REMOTE_DEVICE` and `REMOTE_THREADS` against `LOCAL_DEVICE` and `LOCAL_THREADS`), so that on `ju-TP2` a bare run would ssh to itself and `--local` would decode on `cpu` at `int8` over 12 threads beside an idle GPU. The dotfiles are deployed there, but the tool is driven from `ju-TP`, and the 24/12 counts are measured decisions recorded in `DESIGN-TRANSCRIPTION.md`. The day a run on `ju-TP2` exists it asks for host detection, not for adjusted constants (`transcribe` walkthrough, 2026-10-10)

- In `transcribe-payload.py`, `.amr`, `.amr-wb` or `.webm` missing from `AUDIO_SUFFIXES`, on the ground that `DESIGN-TRANSCRIPTION.md` records PyAV exposing the `amrnb` and `amrwb` decoders. That probe was about the container, and the same note records both recordings as AAC despite their `.3gpp.3ga` extension, so no input carries those suffixes. The consequence would be a `rec.amr.txt` rather than a `rec.txt`, with no overwrite risk, no input name being able to collapse onto its own output (`transcribe` walkthrough, 2026-10-10)

- A `sys-update` module called incomplete for updating only what is present, when the hand-install is documented as the design rather than missing. Measured 2026-10-12 on `uv-tools` and `uv-python`: `rules/install.md` states it outright ("Neither `uv-python` nor `uv-tools` installs anything absent: a fresh machine needs its `uv python install` and `uv tool install` by hand") and contrasts it with the `positron`/`anki`/`libreoffice`/`zotero` modules whose updaters do install, `_meta/notes/dotfiles-bootstrap.md` enumerates the six-tool set and the interpreter step, and `_meta/notes/wsl-init-tuto.md` carries the runnable pair, which is how `ju-TP2` was actually provisioned. A versioned manifest fails "Test the premise before building" on two personally provisioned machines, its only new consumer being drift detection. Read `rules/install.md` and the bootstrap notes before filing an absent install path; the same shape as the `apt-get update` exclusion above, one level up (`/audit:walkthrough --revisit-deferred`, 2026-10-12)
- In `transcribe-payload.py`, `write_outputs` writing `<base>.json` then `<base>.txt` with nothing coupling them, so a stage killed between the two leaves a json claiming diarization beside the unlabelled transcript. The state is recoverable rather than lost: `run_diarize` reads the json back and recomputes both files from its `segments`, which stay authoritative, and a rerun is the whole remedy. `os.replace` from a sibling temp file would close the window and is the shape to use the day a rerun costs enough to pay for it, which on the measured 20.2 min diarization of a 44-minute file it does not. Re-raise only with a reader that cannot tolerate the intermediate state (`transcribe-payload.py` walkthrough, 2026-10-10)

**Why:** these scripts target a known deployment surface (the user's workstation + multi-user servers running the same dotfiles). Threat model excludes cross-UID attackers on the work directory, and operational reality excludes high-frequency automated invocation. Real concerns are functional bugs, not theoretical hardening. The `sys-update` walkthrough (2026-05-10) clarified that for personal wrappers with bats tests, "future-proofing" against hypothetical larger inputs or alternative consumers is not a real concern: the only consumer is the author, who refactors when the need arises.

A module reporting `OK` through `sys-update` while its deliverable is unusable is a real observation but not automatically a bug: check first whether a dedicated always-on detector already covers the condition (`symlinks-check` fails on dangling `~/.local/bin` symlinks, `_meta/notes/dotfiles-bootstrap.md` documents the `npm ci` bootstrap), and whether the module's own contract is narrower than the deliverable (`css-toolchain-update` owns the pin; reifying the tree is `npm ci`'s job). Inventing a distinct exit code plus its mapping in `sys-update` for the summary label alone is not worth it. Note that the "no documented automation consumer" exclusion in the thin-wrapper section below does **not** apply to the `*-update` modules this section covers: `sys-update` is a documented consumer of them, so exit-code semantics findings on a module are not excluded on that ground (the exclusion still stands for `sys-update`'s own output semantics).

**How to apply:** when reviewing files matching `~/dotfiles/bin/.local/bin/*-update` or similar shell installers, drop these finding categories before reporting. **Multi-arch portability IS in scope**: these scripts are deployed on multi-user servers (threat model below), so `amd64`-only assumptions are real bugs. Real bugs that remain in scope: parsing fragility, swallowed exit codes (e.g. trap losing `$?` on cleanup failure), misleading user-facing messages, missing rollback paths, hardcoded arch on a multi-arch deployment surface.

**Threat model on the multi-user servers.** `rv-update` and `quarto-update` live in the dotfiles but are also run, once per host, on multi-user servers. There, assume unprivileged local users: per-file permissions matter (`mktemp` mode `0600` is what blocks tampering in the work directory), and the blast radius of an upstream-trust issue (`curl | bash`, no signature check) is every user the script bootstraps for, so a security finding on these scripts is never rejected on "personal machine, no attackers". Detect the architecture with `uname -m` rather than assume amd64.

For thin install-wrapper scripts in `~/dotfiles/bin/` (e.g. `rv-update`, `sys-update`), also do not raise:

- Version pinning / reproducibility (using `latest` URLs is by design; these wrappers are not configuration management tools)
- Cosmetic locale concerns (Unicode glyphs like `→` `✓` in stderr; modern Linux targets default to UTF-8), and bilingual output matching such as `awk '/désactivé|disabled/'`, which is pragmatic on a French locale with an English fallback: downgrade to Noted unless the script is meant for distribution
- Privilege-model nudges toward user-local default when the script's name signals system-wide intent
- IFS-join robustness on arrays whose contents are statically constrained to validated keys
- `jq` stream deduplication guards (`| first`, `limit(1;.)`) on config fields whose structure is statically constrained to a single value
- Production-grade output semantics on hand-run interactive utilities with no documented automation consumer (meaningful partial-failure exit codes, stdout/stderr separation of diagnostic vs. action lines, pre-flight input validation when the underlying tool's own error message is informative). Surface WARN to stderr is sufficient; `exit 0` at end is acceptable.
- Existence guards (`if [ ! -f "$X" ]`) framed as "config drift invisible" bugs on bootstrap wrappers; the contract of these scripts is "bootstrap files if absent + run the actual update step", not "reconcile generated config on every run". Existence guards intentionally preserve local overrides for paths the user may have edited.
- Config patterns that mirror the upstream's own published recommendation (e.g. `Pin: origin <repo>` taken verbatim from `apt.syncthing.net`'s troubleshooting block); diverging from upstream's documented form adds maintenance debt with no real security gain.

Excluded: this section does **not** disable findings on integrity verification before `sudo sh` execution; those remain in scope (coupled to the pinning decision).

For Claude Code hook scripts in `~/dotfiles/claude/.claude/hooks/` (e.g. `inject-project-context.sh`) and the `commit` skill's scripts in `~/dotfiles/claude/.claude/skills/commit/scripts/`, do not raise:

On an injector, `set -e` would abort the script on any failed `grep` (exit 1 when no match), leaving Claude with no context rather than partial context
- Quoting / word-splitting findings already cleared by `shellcheck`; shellcheck is the authoritative reference. If it passes, the finding is a false positive
- Portability concerns (GNU sed `\s`, etc.); target is Ubuntu 24.04 with GNU tools
- In `write-journal.sh` / `commit-gate.sh` / `commit-stale.sh`, the journal "missing" Bash writes (`sed -i`, heredocs) or `NotebookEdit`: the Bash gap is documented with its fallback routes in `.claude/PLAN-SESSION-DISCIPLINE.md` § « Écritures hors Edit/Write » and covered by the CLAUDE.md rule routing every write through Edit/Write and, since 2026-09-23, mechanically in the project repo by the gate's union of the journal with `git status`; since 2026-09-27 the guard and the gate's verdict on fenced blocks read the `git status` of the commit's own repository, whatever it is, the journal union surviving in the gate's fallback only; no user-authored `.ipynb` exists on the machine (only vendored copies under `~/.vscode` and `~/.cache`). Re-raise only with a measured Bash-only write that a commit took and that escaped both the guard and the gate (`commit-gate.sh` walkthrough, 2026-09-22). One such shape, a write earlier in the command holding the commit, was accepted on 2026-09-27 as data integrity (outside this calibration) and is now refused by `git-write-guard.sh`, which lets a command holding `git commit` run only `cd` or `pushd`, a `SKIP=` prefix, and git add, rm, mv or commit, a segment made only of assignments counting as another command, both of those forms pinned in the refusal loop of `git-write-guard.bats`; do not re-raise that shape
- In `commit-gate.sh`, the trigger pattern missing a commit split by a backslash continuation: `git commit \` then `-m` matches, as do a continuation before `git` and one after `-m`, so only a continuation between `git` and `commit` slips, and its only occurrences in the retained transcripts were the walkthrough's own probe command. The guard reads all four forms and `SKILL.md` renders the commit line whole. Re-raise only with a continuation between `git` and `commit` measured in a transcript that is not a walkthrough probe (`commit-gate.sh` walkthrough, 2026-09-28)
- In `skills/commit/scripts/writes.sh`, filtering the journal by the stored stamp "as `commit-stale.sh` does", to spare the verifier on a second `/commit`: `verifier.md` defines `WRITES` as every path written during the session, and its re-derivation of tracking claims needs the files written before the stamp. The gate and the verifier filter differently on purpose (`writes.sh` walkthrough, 2026-09-24)
- In `commit-stale.sh`, `--seal <n> --carry` dropping every carried seal when `n` equals the value already in the stamp file: the group's redirection truncates the very file the carry then reads, in silence and at exit 0. Measured, and unreachable through the only caller, `writes.sh` minting `date +%s%N` in the same pass, so a guard would protect nothing that exists. Re-raise only with a caller passing a value it did not mint itself, or a stamp at second resolution (`commit-stale.sh` walkthrough, 2026-09-30)
- In `commit-stale.sh`, the untested `printf`s of the seal group, whose status comes from its trailing `if ((carry))`, so a partial write leaves a truncated snapshot at exit 0 while the stamp still moves. All four truncation shapes were traced on the read side (missing header, missing row, cut digest, cut path) and each falls back to `changed` or `unsealed`, never to silence, so the direction of the degradation is itself the guard. Re-raise only with a truncation measured to under-report (`commit-stale.sh` walkthrough, 2026-09-30)
- In `commit-stale.sh`, a guard refusing a named path that `--seal --carry` records as absent, proposed so that a `--restamp` naming a path which resolves nowhere stops reporting success. Written, measured and reverted on 2026-10-10: the condition "absent and not held by the previous snapshot" also catches a file the session created after the seal and then deleted, which `--only` reports `changed` and which the guard then refuses to clear, where a restamp cleared it before. Narrowing it to "and absent from the session's own journal" does work and was declined on cost: a journal read inside the seal path, against a diagnostic gain of one step, the path the model meant staying reported by the very next check, which the skill's own step performs. What was kept is the `commit/SKILL.md` wording, which promised a notice this case never produces. Re-raise only with a loss measured that the next check does not surface (`commit-stale.sh` walkthrough, 2026-10-10)

The mention loop is quadratic in the token count (0.13 s at 500 mentions against 4.04 s at 4000), and a filesystem path matches none of it, `/home/julien/dotfiles` producing no token, so the trigger would be a prompt listing thousands of slash-command-shaped words against a corpus maximum of 8. **Why hook scripts:** walkthrough on `claude/.claude/hooks/inject-project-context.sh` (2026-05-08): 5 of 7 findings rejected. The hook's design is deliberately best-effort; fail-fast patterns are counterproductive here.

**How to apply (hook scripts):** flag actual logic bugs (wrong exit-code semantics, incorrect grep anchors, empty-output when non-empty expected). Do not propose defensive patterns that conflict with best-effort output intent.
