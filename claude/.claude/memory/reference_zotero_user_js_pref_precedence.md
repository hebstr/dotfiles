---
name: Zotero's stow-managed user.js reverts every preference pane change
description: Why a Zotero or Better BibTeX preference set in the settings pane reverts at the next restart, which file to read first, and the citation key facts measured alongside it
metadata:
  type: reference
---

The Zotero profile `~/.zotero/zotero/pucr7b5d.default/` is stow-managed and resolves into `~/dotfiles/zotero/`. It holds both `prefs.js`, which Zotero writes, and `user.js`, which Zotero **reads and re-applies at every startup**. A preference the settings pane changes lands in `prefs.js` and works for that run; if `user.js` declares the same key, the next start overwrites it, with no warning anywhere in the UI.

Established 2026-09-29 on the Better BibTeX citation key formula: `prefs.js` carried `auth.lower + "_" + year` while `user.js` carried `auth.lower + shorttitle(3,3) + year`, and items added on 2026-09-22 had keys in the `user.js` format, so a pane change had been silently undone at an earlier restart. Watched live the same day: `prefs.js` was rewritten back to the `user.js` value at a 14:57 restart.

This supersedes the 2026-09-23 resolution in `~/dotfiles/_meta/notes/zotero-agent-access-reco.md`, which saw the same symptom (keys not following `citekeyFormat`) and stopped at "l'utilisateur avait changé la formule à la main". The manual change was real; what that note missed is why it did not survive, which is this file precedence.

**Never open `user.js` in the editor without checking what a formatter did to it.** On 2026-09-29 a Positron save ran Prettier over it (`"[javascript]"` → `formatOnSave` with `esbenp.prettier-vscode`, and the file ends in `.js`), which rewrapped seven `user_pref(` calls across lines and added a **trailing comma after the value**. The Firefox preferences grammar (`modules/libpref/parser/src/lib.rs`) allows `("," <pref-attr>)*` only in *default* pref files, never in a user pref file, so `false,)` is a syntax error; multi-line calls and single-quoted strings are both fine, the comma alone is fatal. The failure is silent and masked: every pref that already lived in `prefs.js` kept working by inertia, and only the one pref declared solely in `user.js` (`resetKeyOnChange`) never applied, which cost a regenerated citation key. Guard added the same day: `~/dotfiles/.prettierignore` with `**/user.js` and `**/prefs.js`, verified by `prettier --check` passing with it and failing under `--ignore-path /dev/null`. It is deliberately repo-wide rather than scoped to `zotero/`: the only two versioned `.js` files in dotfiles are this one and Firefox's `user.js`, both Mozilla prefs files (the other 812 sit under the gitignored `css/.local/share/css-gate/node_modules/`, which Prettier ignores by default), so the broad glob catches nothing else and covers a future Mozilla-profile package for free. **Firefox's `user.js` was never damaged, but only by accident**: Prettier wraps at 80 columns, and its four prefs are at most 75 characters, where the Zotero file carried, before the 2026-09-29 reformat, two lines of ~2 140 characters (the Sci-Hub resolver lists) plus four between 94 and 103 (1 803 and 1 800, and four between 92 and 103, once the escaped double quotes became single quotes). One long pref added to the Firefox file and it breaks identically. In a repo that held real JavaScript, scope the glob to the package. It is enough, because the file is always edited at its resolved dotfiles path and `~/dotfiles` is one of this profile's Positron workspace roots: `esbenp.prettier-vscode` 12.4.0 resolves the ignore path through `getWorkspaceRelativePath`, which returns `undefined` unless `workspace.getWorkspaceFolder(file)` matches, and here it matches. A second guard (a `files.associations` entry taking the file out of the `"[javascript]"` block) was added and then **removed as unnecessary**: the only holes it closed are editing through the `~/.zotero/...` symlink, which the dotfiles symlink rule already forbids, and editing from the `~` workspace root, which has no `.prettierignore`. Do not re-propose it. The same trap applies to any Mozilla prefs file edited in a VS Code-family editor, where the guard has to sit wherever that editor's ignore resolution can see it.

**Read `user.js` first, never `prefs.js`.** A key in both means `user.js` wins and `prefs.js` is a decoy. A key in `prefs.js` only means the pane is authoritative. The cheapest proof that a pane change never took is the artifact, not either file: here, the citation keys of recently added items. Set the value in `user.js` at its resolved dotfiles path, and restart Zotero for it to apply.

**eds-prise settled its own formula on 2026-09-29** in that repository's `.claude/DESIGN-BIB.md`: `user.js` takes `auth.lower + year`, which yields a short lowercase key (`lucas2022`), not the `Auth_Year` convention `index.qmd` cites: every key still has to be hand-set, since a citation key is case-sensitive and a lowercase one breaks the citation silently. A first pass that same day set `auth + "_" + year`; `auth.lower + year` is what stands, measured at 19:28 on both `user.js` and `prefs.js`. Existing keys do not move, Zotero 8+ keeping every key pinned in a native field. The formula serves the articles only: the five HAS suffixes (`_reco`, `_argu`, `_fiche`, `_snds`, `_eds`) stay hand-set on the eight HAS records, since `auth.lower + year` cannot separate them and BBT would only add a meaningless disambiguation letter. An earlier section of that same note, "L'état constaté avant bascule", records the pre-decision state and argues against the change: it is superseded, and reading it as current is how this session wrongly reverted the formula once.

Citation key facts measured on the same library (315 top-level items at 2026-09-28, 211 with an author; 317 at 2026-09-29, all 317 carrying a `citationKey`), true whatever the formula:

- `auth` gives the first author's last name as stored; `.lower` alone lowercases it.
- Diacritics fold to ASCII in keys with no filter (`Munafò` gave `munafo…`, `Vergnenègre` gave `vergnenegre…`), so `.transliterate` is redundant for that purpose.
- A single-field institutional creator (`"name": "Haute Autorité de santé"`) enters `auth` whole: no formula yields `HAS`.
- Changing the formula never regenerates existing keys (BBT docs: "existing keys are not automatically regenerated when you change the pattern"); only a per-selection right-click "Refresh" does. **One exception:** `extensions.zotero.translators.better-bibtex.resetKeyOnChange`, build default `false`, was found `true` in `prefs.js` on 2026-09-29 with nothing in `user.js`, so it had been set from the pane. Read in the installed 9.0.64 build: the `items-changed` handler calls `update(item, { replace: Preference.resetKeyOnChange })`, and inside `update()` the guard `if (current && !replace) return` then stops protecting the native key, which is regenerated and saved on *any* item edit; only an edit of the key field itself is protected, by an earlier branch. **The user declared it `false` in the versioned `user.js` the same day**, together with `extensions.zotero.cite.automaticJournalAbbreviations`; Zotero has restarted since, and `prefs.js` no longer carries the key at all (verified 2026-09-29, Zotero closed): the declared value matches the build default, so the pane wrote nothing back. `fillKeyAfter` (1 here, 2 by default) is the auto-pin delay; at `0` keys are generated on request only.
- Key clashes take an automatic `a`/`b`/`c` postfix that cannot be disabled, which is what `shorttitle` in the default formula exists to avoid. Real clashes in this library: Bewick ×3 in 2004, Vergnenègre ×2 in 2004, plus Curran-Everett, Ioannidis, Marill, Pham, Whitley.
