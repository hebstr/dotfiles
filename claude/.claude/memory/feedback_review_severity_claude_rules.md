When reviewing or auditing `.claude/rules/*.md` files (path-scoped rule files loaded by glob via `paths:` frontmatter), do **not** propose any of the following:

1. **Flagging the R/Python idioms in rule files as CLAUDE.md duplication, or proposing to move them back.** CLAUDE.md is loaded globally on every conversation; rule files are loaded only when their glob matches. The idiomatic conventions (pipe `|>`, `here::here()`, polars-over-pandas, etc.) now live canonically in `rules/r.md` and `rules/python.md`, removed from CLAUDE.md so the global file stays lean and the idioms load only when an R/Python edit matches the glob. They no longer duplicate CLAUDE.md. Do not propose relocating them back into CLAUDE.md or deleting them as redundant.

2. **Deduplicating boilerplate phrasing across rule files.** Patterns like "Mandatory pipeline after every create/edit" appear in multiple files with slight phrasing variation. This is intentional locality: each rule file is self-contained by design. A reader (Claude) sees one file at a time, not three. Normalization buys nothing.

3. **Per-file version-trace headers.** Lines like `# Verified against ruff X.Y / jarl X.Y, 2026-05` rot fast and lie within a quarter. The global CLAUDE.md rule "verify against current docs before writing" already covers this concern as behavior, not annotation.

4. **Mixing review-calibration content into writing-rule files.** Review tolerance and severity calibration belong in `feedback_*.md` memories (e.g., `feedback_review_severity_shell_installers.md`). The `rules/*.md` files describe how to write/edit code, not how to review it. The two scopes are orthogonal; mixing them dilutes both.

5. **Proposing removal of an alternate tool because it partially overlaps with the main pipeline tool.** Rule files often document a primary tool plus auxiliary commands (e.g. `python -m py_compile` next to `ruff check`; `--check` next to `ruff format`). Auxiliary tools in their own section signal "use when X, not as part of the mandatory pipeline": they are intentional optionality, not redundancy. Suggestions like "ruff check already does syntax parsing, remove py_compile" treat documented alternatives as bloat and narrow the toolchain for no gain. This covers *removal* only, not *scoping*: `py_compile` genuinely false-passes on a `.ipynb` (it compiles the JSON envelope, exit 0, while `ruff check` reports the cell's syntax errors), so a line bounding it to `.py`/`.pyi` is a real finding and was applied 2026-07-28.

6. **Flagging the prek `^bash/` exclusion as conflicting with shell.md's auto-load/format scope.** The `bash/` stow-package dotfiles (`.bashrc`, `.profile`, `.bash_aliases`) are kept out of the *commit-time* hooks, but the user accepts Claude formatting them locally (shellharden/shfmt/shellcheck are safe on them). The prek `^bash/` exclusion is a commit-gate scoping choice, not a prohibition on local formatting, so editing a `bash/` dotfile may auto-load `rules/shell.md` and run its gate. Do not flag the `paths:`-includes-`.bashrc` vs prek-excludes-`^bash/` pairing as a contradiction.

7. **Flagging a rule as "ambiguous", "subjective", "missing guidance", or "unenforceable" when the same file already operationalizes it.** Before calling a rule incomplete, read the whole section: the operationalization is often already present as a positive+negative list (e.g. the `substantive`/`not substantive` lists gating `/audit:blindspot`), a flags table documenting the strict option (e.g. `-D warnings` for Rust), or an uncertainty fail-safe ("when uncertain, treat as substantive"; "default to feedback memory"). A subjective boundary handled by a documented safe default is correct design, not a defect. This also covers forcing-function meta-rules ("Test the premise before building"): they have a decidable core (name the consumer) even when they read as abstract.

8. **Proposing to widen a rule file's `paths:` glob so it auto-loads on a format whose gate is enforced mechanically.** Example: `rules/quarto.md` documents the panache gate that also covers plain `.md`, yet its `paths:` matches only `.qmd` and Quarto YAML. That is correct: the gate runs from the `format-on-edit` hook and the prek hook regardless of what Claude has loaded, `CLAUDE.md` carries the actionable part, and the rest of the file (render gate, chunk handling, Typst notes) would be dead weight in every markdown edit of every project. The reference content matters when *configuring* the formatter, which is a deliberate on-demand read.

9. **Flagging `ruff` as missing from the one-tool-one-binary set.** `python.md` and `r.md` document a pin for `pyrefly` (`pyrefly.lspPath`) and `air` (`air.executableStrategy: "environment"`) because those extensions ignore the PATH or default to their bundled copy. The `charliermarsh.ruff` extension defaults to `ruff.importStrategy: "fromEnvironment"`, documented upstream as "Use `ruff` from environment, falling back to the bundled version if `ruff` is not found", and contributes no terminal environment collection. It already resolves the managed binary, so it needs no pin, and no row in `environment.md`'s table, which records pins rather than duplicate copies on disk.

10. **Flagging a convention shared by every rules file as a per-file defect.** The heading "Mandatory pipeline after every create/edit" is a template repeated verbatim across the eight `rules/*.md`. Section ordering differs between files without consequence, since each loads in full. Qualitative judgment language ("occasional", "flag but do not auto-correct") is the house idiom for non-mechanical guidance. Restating an always-loaded `CLAUDE.md` rule inside a scoped file is the mirror image of the same error: `CLAUDE.md` already carries the gate's scope predicates and its failure policy, and governs both by its own conflict clause. Editing one file's copy breaks the template; editing all eight is the normalization pattern 2 already rejects.

11. **Portability hedging for platforms or tools absent from the machine.** `**/*.pyw` on a Linux-only box, or a caveat that `.venv/bin/python3` might be `venv/` under poetry or pdm when `environment.md` declares `uv` the sole Python package manager and `uv venv` defaults to `.venv`. These read as thoroughness and add a branch nothing here can take.

12. **Proposing `hasattr` over `from pkg import fn` for the import-existence check.** The reverse holds. `from pkg import name` falls back to an implicit submodule import when `name` is not yet a bound attribute, so `from xml import etree` succeeds while `import xml; hasattr(xml, "etree")` returns `False`. The idiom already in `rules/python.md` is the more robust of the two.

13. **Flagging the `&&` chain in `r.md` or `shell.md` as the defect fixed in `python.md`.** Probed 2026-07-28: `air format` on unparseable R exits 255 without mutating, `shfmt -w` on unparseable shell exits 1 without mutating, and `shellharden --replace` exits 0 in every case tested, mutating even on unparseable input. None of the three ever mutates a file *and* exits non-zero, so `&&` there aborts only on a genuine hard failure, which is the intended behavior. The Python case was specific: `ruff check --fix` is a linter that reports residual violations through its exit code, so it mutates and exits non-zero on ordinary churn. Pure rewriters have nothing to report.

**Why:** the 2026-05-10 walkthrough on `claude/.claude/rules/` produced 14 findings, 6 of which (43%) were false positives matching exactly the first four patterns. The 2026-05-16 walkthrough on `rules/python.md` added pattern 5: a Suggestion to remove `python -m py_compile` because `ruff check` covers syntax parsing. The 2026-06-03 blindspot walkthrough on `CLAUDE.md` + `rules/` added patterns 6 and 7: the cross-model (Gemini) pass mostly produced pattern-7 false positives (flagging `-D warnings`, the `substantive` lists, and "Test the premise" as missing/ambiguous when each was already operationalized in-file). These patterns sound disciplined but produce bloat, duplication, or rotten lines.

The 2026-07-23 `/workflow:sync` walkthrough added pattern 8 (widening `rules/quarto.md`'s `paths:` to `**/*.md`).

The 2026-07-28 `/audit:blindspot` + walkthrough on `rules/python.md` (Gemini external) walked 24 findings and rejected 9, adding patterns 9-12. Note that pattern 8 did **not** cover the config-file globs accepted that round (`pyproject.toml`, `pyrefly.toml`, `ruff.toml`): a rules file loading on its own toolchain's config is the established shape, as `quarto.md` already does for `_quarto.yml` and `shell.md` for `.bashrc`. Pattern 8 targets widening to a different *format* whose gate is mechanical, not adding the toolchain's own config.

**How to apply:** in any future audit of `.claude/rules/`, skip these thirteen categories of suggestion immediately. They are recurring false positives, not actionable findings. Real findings still apply: factual errors in commands/flags, content stale relative to checked-in configs, scope mismatches (e.g., IDE setup polluting per-edit rules).
