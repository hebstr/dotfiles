**trigger_consensus cross-model:** Only `ouroboros_evaluate` supports `trigger_consensus: true` for cross-model consensus via OpenRouter. `ouroboros_qa` does NOT: the parameter is silently ignored, producing a same-model result that looks cross-model but isn't.

**Why:** Discovered 2026-03-31 during review-walkthrough session. The skill incorrectly instructed using `ouroboros_qa` with `trigger_consensus: true`.

**How to apply:** Cross-model consensus → `ouroboros_evaluate`. Same-model QA → `ouroboros_qa` without `trigger_consensus`. But read the correction below before counting that consensus as cross-model.

**Corrected 2026-09-15: under the plugin's own MCP launch, that consensus is not cross-model either.** The Ouroboros plugin's `.mcp.json` (0.54.4) starts the server with `--llm-backend claude_code`, and `ClaudeCodeAdapter._normalize_model` maps every `openrouter/<non-anthropic>/...` voter to `None`, the default Claude model. The CLI transcripts of the three votes of one 2026-09-15 round were all `claude-opus-5`, while the result labelled them `gpt-4o`, `claude-opus-5`, `gemini-2.5-pro`: the label is the requested model, not the served one. Editing `consensus` in `~/.ouroboros/config.yaml` changes nothing under that backend, and the `litellm` backend is not a way out, its extra being pinned to `python_version < '3.14'` while the plugin launches 3.14. For a real cross-provider verdict, call OpenRouter directly, as `audit:walkthrough` L2 does since that date with `audit/walkthrough/scripts/openrouter-verdict.py` (see [[feedback_audit_walkthrough]]). Every L2 consensus count recorded before that date, in the `feedback_review_severity_*` files included, is therefore intra-family agreement. Versions before 0.54.4 not checked.

The rest of this file governs what still calls Ouroboros in a walkthrough: the Step 3 evaluate and the drift check, both with `trigger_consensus: false`.

**`ouroboros_evaluate` reads `working_dir` from disk, so it must finish before any edit.** It does not judge the `artifact` in isolation: it opens the files, greps them, and quotes their live line numbers back. A call left running while the fix lands therefore evaluates the *corrected* code and returns APPROVED, which reads as "the finding is a false positive" and is the opposite of what happened. Observed 2026-07-27 on an edstr walkthrough. It also takes 2 to 5 minutes and backgrounds past the 120 s tool timeout, so the temptation to edit meanwhile is the default path. Sequence it: evaluate first, edit after; if the two overlap, discard the verdict. Otherwise launch it and keep working rather than blocking on it.

**Stage 1 runs the project's test command and can destroy its env.** Stage 1 is mechanical and hard-gating: it runs the command the detector wrote to `<project>/.ouroboros/mechanical.toml` on the first call (a bare `uv run pytest`), which in `eds-avc` synced the env, purged the editable `edscrib` install and failed every test, so the call never reached the semantic stage (2026-07-28). Fix the command in that file (`uv run --no-sync pytest`) rather than skipping the mechanism, and gitignore `.ouroboros/`. Add no other key (`lint`, `build`, `static`, `coverage`): each is one more way to never reach Stage 2, and the executable allowlist holds no `pyrefly`, so a `static` entry is silently skipped and reported as passed. Stray artifacts of a call: that file and `.claude/.ouroboros_eval_artifact.md`.

**The input filter rejects source text, and the artefact form decided success.** `ouroboros_evaluate` refuses an artefact holding the literal `open(` (`Potentially dangerous input in artifact`) and flagged `'/.../x'` as path traversal. Sessions whose artefacts described the code in prose ran clean four times running on `0.50.5` (2026-07-30 to 2026-08-02), where earlier sessions pasting source hit `Missing required fields: [...] (field: response, value: None)` at Stage 2 on every call. This conflicts with `audit/walkthrough/agents/ouroboros-bridge.md`, which says "Build `artifact` from actual content, not prose" and keeps prose as the fallback; the conflict is unresolved there. On a `Missing required fields` failure, retry once with a leaner artefact, then declare the tool unavailable for the walkthrough with the stage and reason, and carry the verdict on L1 plus empirical reproduction. Two other failure modes seen: `Claude Agent SDK reached max turns`, and an OpenRouter spend or session limit.

**`ouroboros_measure_drift` needs `current_concepts`, and its goal component measures approved scope.** Without `current_concepts` against the bridge's placeholder `ontology_schema`, the ontology term saturates at 1.00 and alone pushes the total past the 0.3 threshold; with them it reads 0.00 (2026-09-21). The goal component compares against the approved goal, or the previous commit's message when no PR exists, and scores an approved broadening as drift. On a walkthrough, read the constraint component as the signal, and treat a high goal component as a prompt to list the scope extensions and check each has an approval.
