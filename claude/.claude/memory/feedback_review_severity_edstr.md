Package-specific review dismissals for edstr, supplementing [[feedback_review_severity_personal]]. Scope: the R package at `~/Documents/packages/R-edstr` (clinical concept extraction over EDS clinical notes).

**Why:** recurring false positives on documented design boundaries a reviewer re-flags each pass. The 2026-07-22 cross-consistency scan rejected 4 of 11 findings, all for the same reason: an apparent inconsistency filed without first checking the semantics, the scope, or the actual state.

**How to apply:**

- **`easy_format()`'s HTML-body regex `regex("\">(.+?)</p>", dotall = TRUE)` is correct as written** (`R/extract_helpers.R`, inside `.extract_format_text`). The `">` anchor requires an attribute quote before the closing `>` of the opening tag, i.e. it matches `<p class="...">content</p>` but NOT a bare `<p>content</p>`. This is intentional: EDS export `<p>` tags **always** carry an attribute (author-confirmed 2026-07-21). Do NOT flag "the regex ignores bare `<p>` tags / misses `<p>` without attributes" as a bug: bare `<p>` does not occur in the real EDS format. Documents that yield no text after formatting are surfaced as the `unmatched$empty_text` and `unmatched$outside_p` buckets (the earlier `cli_warn()` guard was removed in the 0.3.0.9000 cycle and no longer exists anywhere in `R/`). The `dotall = TRUE` + non-greedy `(.+?)` were added 2026-07-21 so a single `<p>` whose content spans multiple lines is captured; greedy `.+` without dotall was the prior truncation bug and is fixed, so do not re-propose it either.

- **`edstr_extract(token=)` and `edstr_view(ngrams=)` are different concepts, not an API naming inconsistency.** `token` is an `<integer>` **vector** of n-gram sizes fed to `unnest_tokens(token = "ngrams", n = n)`; `ngrams` is an `<integer(1)>` regex window width used to build `"{pattern}(?:[\s\-/]+\w+){0,{ngrams-1}}"`, and `edstr_view()` does not tokenise at all. Unifying the names would give one identifier two semantics and two arities. Do NOT propose renaming either one. The genuinely inconsistent pair is `edstr_clean(text=)` vs `edstr_extract(text_input=)` (same concept, two names), which is already tracked in the project's `DEFERRED.md` and needs a lifecycle deprecation, not an ad-hoc rename.

- **Gitignored working files are out of review scope.** `dev/TODO.md` is a personal French shorthand scratchpad; `cran-comments.md` is a submission artifact regenerated at submission time. Neither is published, read by a third party, or loaded by tooling. Do NOT flag stale vocabulary, retired symbol names, or drift against the code in them. `dev/TODO.md` goes further than out-of-scope: it is not to be opened at all absent an instruction naming it ([[feedback_personal_working_files]]), so it is skipped and reported as such, never read and then exempted. The exception is the three files the project CLAUDE.md's Index designates as references to read (`.claude/CLAUDE.md`, `.claude/PERF.md` before touching a matching stage or re-benchmarking, `.claude/DEFERRED.md` before triaging deferrals): factual errors there (wrong measurements, wrong artifact sizes, stale `file:line` anchors, work recorded as done that is not) are legitimate findings, and `/audit:walkthrough --revisit-deferred` consumes `DEFERRED.md` as an input source, so a false statement there misdirects the next pass. The same exception covers `.claude/PLAN.md`, which exists and is maintained (87 lines as of 2026-07-25): it describes itself as "the short answer to what is live right now" and points at `DEFERRED.md`, `PERF.md` and `PERF_ROUND3.md` rather than duplicating them. An earlier version of this rule claimed the file had been removed on 2026-07-23; that was wrong, and the project `CLAUDE.md` Index does not list it either, so a reviewer told to expect no `PLAN.md` will silently skip the one file describing the live state.

- **An index or summary row that enumerates a document's section names asserts nothing about their live state.** The project CLAUDE.md Index describes `PERF.md` as "closed record of both perf campaigns: measurements, the re2 and hybrid-fold recipes, the invariants the code rests on, the settled decisions". Those words are a section inventory (`PERF.md` has `## Results`, `## The hybrid fold`, `## Invariants the current code rests on`, `## Decisions that must not be re-litigated`), not a claim about what any section currently says. The same trap was filed against `PLAN.md`, whose Index row ended on "blocker" while the document marked that blocker RESOLVED. Check whether the listed words map to headings before reading them as state.

- **A `Suggests` entry whose only consumer is an `.Rbuildignore`d dev file is correctly declared.** `rmarkdown` has no call site in `R/`, `tests/` or `vignettes/` (the vignette engine is `quarto::html`), but `README.Rmd` declares `output: github_document`, exported by `rmarkdown`, and `devtools::build_readme()` is a live workflow here (`README.Rmd` and `README.md` move in the same commits). `.Rbuildignore` excludes a file from the tarball, not from the development workflow, and `Suggests` is exactly where such a dependency belongs: not installed by default, no `R CMD check` note. Before filing "unused dependency", grep the YAML headers of `.Rmd`/`.qmd` files and `data-raw/`, not just `R/`.

- **The CI workflows do not have a missing Pandoc/Quarto setup step.** `r-lib/actions/setup-r-dependencies@v2` provisions both transitively: it downloads `quarto-dev/quarto-actions` (`install-quarto: auto`, `quarto-version: release`, `pandoc-version: 3.8.3`) and its sysreqs resolution apt-installs `pandoc` and `default-jdk`. The absence of an explicit `setup-pandoc@v2` in `R-CMD-check.yaml`, where `pkgdown.yaml` has one, is redundancy avoided, not an oversight. Verify against `gh run view <id> --log` before filing any CI-provisioning finding.

- **The nested-concept crash is a doc + downstream-guard matter, not a `.extract_parse_concepts` bug.** A 2026-07-24 review flagged `list(cancer = c(sein = "...", poumon = "..."))` as a defect in `.extract_parse_concepts` or the `map_chr` at `extract_helpers_match_token.R:91`; that root-cause is wrong. `.extract_parse_concepts` is correct and matches `test-extract_helpers.R:160` ("nested list keeps single root key"). A `c()`-leaf root (several patterns under one root) is only valid with `collapse = TRUE` **and** ≥2 roots (it OR-merges per root, see `test-extract_helpers.R:62`); under the default `collapse = FALSE` it leaves a length-2 pattern vector on one root, which `token_extract` feeds to `str_extract` and crashes ("Can't recycle string to match pattern"), reached *before* line 91. To track sub-concepts separately use the `list()`-leaf form `list(cancer = list(sein = ..., poumon = ...))`, which flattens to distinct keys `cancer_sein`/`cancer_poumon`. Do NOT re-file this as a `parse_concepts`/`map_chr` defect.

- **`.extract_parse_concepts` stays permissive on purpose; the refusal lives in `edstr_extract`.** The parser accepts a multi-pattern `c()`-leaf root and returns a 2-row `regex_df` for it, which `test-extract_helpers.R:160` pins. Moving the guard *into* the parser breaks that test, and the 2026-07-24 walkthrough did exactly that before reverting: read the test before touching this split. Guard history: the roxygen example was corrected to the `list()` form and a guard added in `edstr_extract` (2026-07-24); the same walkthrough then found it only covered a **single** root, because `tibble` recycles a length-1 `keys` column to length 2 while 2-vs-3 cannot recycle, so ≥2 roots died earlier on `Tibble columns must have compatible sizes`. The guard now runs **before** `.extract_parse_concepts`, discriminating atomic from `list()` leaves with `!map_lgl(concepts, is.list) & lengths(concepts) > 1`, and both root counts yield the same actionable message.

- **`edstr_extract` reserves five column names in `data`, checked up front in `.extract_check_ids`.** `n`, `concept`, `extract`, every concept key, and `id_group` (the last only when `group` is `NULL`, since an explicit `group` leaves a user `id_group` untouched). Before the 2026-07-24 guard, `extract` and `id_group` were silently overwritten and a concept-key homonym was split into `<key>.x`/`<key>.y`, while `n` and `concept` aborted deep in the assembly. `.extract_check_ids` therefore takes a `concept_keys` argument, and `concepts` must be parsed before it is called; `demo/extract_refactoring_test.R` calls it directly too.

- **A latent fragility in an internal helper, verified unreachable through the public API, is DEFERRED, not fixed.** Established policy, three instances now in `.claude/DEFERRED.md`: item 20 (`set_class_css()` losing a default-ignorable code point, "correctif connu et à 2 lignes" and deferred anyway), item 21 (`.re2_prepare()` on an `NA` in `text`), and the 2026-07-25 `.pua_guard()` item (`any()` returning `NA`, one-word fix `na.rm = TRUE`). The cost of the fix is not the criterion; the criterion is that nothing reaches the path, so a guard there is dead defensive code. Before filing one of these, verify the reachability claim yourself by tracing the caller, then defer with the trace recorded. If the series is ever to be cleared, clear all three in one pass rather than one at a time.
  **Do not stretch this rule to cover a documented public argument.** The 2026-07-27 walkthrough saw it invoked as the author's defense on three findings and rejected on all three: the criterion is unreachability through the public API, not absence from the author's current corpus. `regex_replace` is an exported, documented `edstr_extract()` argument the vignette invites the user to extend, so a defect that needs one is reachable, whatever the `avc` corpus does. A corpus-wide check ("verified on 4215 triples", "measured on 7883 documents") establishes nothing about a code path that corpus never exercises: two such checks in `DEFERRED.md` and `SOURCE_ALTERNATION.md` were sound as statements about `avc` and unsound as the guarantees about the code they were written as. The corollary cuts both ways and is worth holding onto: re-running the goldens after those two fixes returned the corpus output unchanged, so a defect can be real, unit-pinned, and invisible on the corpus at once. Do not read a green golden as "the finding was a false positive", and do not read a reachable defect as "the goldens must move".

- **CRAN submission state is not a defect.** `edstr` is not on CRAN (verified against the CRAN index 2026-07-25; its 0.1.0/0.2.0/0.3.0 releases are GitHub releases, and the README carries no CRAN badge). Two review findings were rejected on this ground and will recur: `Version: 0.3.0.9000` paired with `# edstr (development version)` in NEWS.md, filed as a Blocking "cannot be submitted", and the README's "edstr is not on CRAN. Install from GitHub", filed as contradicting the package's CRAN page. Both describe **release actions** performed by `usethis::use_version()` at submission time, not defects present in the repo, and NEWS.md shows three prior cycles reverting to "(development version)" exactly as the convention prescribes. The README claim is moreover *true*: applying the proposed fix would write `install.packages("edstr")` for a package that cannot be installed that way. Do NOT file either again while the package is unpublished; if a submission is genuinely in flight, say so as a checklist item, not as a finding.

- **Method rule for cross-consistency scans on this repo.** Before filing "X and Y disagree", establish which one is right by reading the code, and check that both surfaces are in scope. Grep-level similarity (two arguments with related names, a doc string that differs from another doc string) is a lead, not a finding. Where a claim is measurable, measure it: a full `devtools::check()` takes ~3 min and settles most metadata and packaging suspicions outright.
