  type: feedback
---

When reviewing bats `.bats` test files for personal shell tooling (e.g. `_meta/tests/*.bats` covering scripts under `~/dotfiles/bin/.local/bin/`), do NOT raise the following finding patterns:

- Failure-injection coverage for `cmd || warn …` bash idioms where the error branch is a one-liner printf-to-stderr: testing this exercises bash's `||` operator, not application logic
- Non-dry-run mutating-path coverage when the script gates the path behind `sudo` re-exec and `EUID != 0` checks: adding coverage requires either running tests as root or building fake-EUID infrastructure, disproportionate for personal Ubuntu tooling whose author always inspects with `--dry-run` first
- Pinning known script-level bugs as test expectations during a test-file walkthrough: that obstructs a future fix; out of scope for a test-file review
- Cosmetic `${VAR:-}` defaults or `rm -rf --` in setup/teardown when the current code is correct under bash quoting rules and the unsafe-input scenario (paths starting with `-`, or unset variables triggering `set -u` paths) cannot occur (`mktemp -d` never produces leading-dash paths, and `rm -rf ""` is a no-op)
- Per-function narrowing of file-level `# shellcheck disable=SC2030,SC2031`: file-level disable is the standard bats idiom because each `@test` runs in a subshell, triggering these warnings on variables legitimately set in `setup()`
- "Production-grade error handling" for `run` wrappers and interactive `read -r -p` prompts whose only realistic regression class would require bash itself to break
- Stub-fidelity coverage whose only consumer is the stub itself: teaching a stub to mutate a file the script never re-reads (e.g. an `npm` stub rewriting `package.json` devDependencies so a test can assert "the pin moved") asserts the test double's programmed behaviour, not the code. Same for sequential "run it twice" idempotency tests that reach a branch a fixture already covers. Both remedies are also circular: the second depends on the first, which exercises nothing
- `bats_require_minimum_version` directives on a suite that uses no version-gated feature (`run -N`, `run !`, and the rest of the Bats 1.5 surface): the directive pins a constraint nothing exercises. Counted 2026-09-28: 15 of the 54 suites here carry one and 12 use such a feature, those 12 all carrying it, so its absence is the house majority, not an oversight, and its presence is warranted exactly when `run !`, `run -N` or `run --separate-stderr` appears
- Guards for a state only the stub can produce: when a stub writes less than the real tool does (e.g. `npm install <pkg>` reifies the whole tree from `package.json`, the stub writes only the named packages), the resulting anomaly in script output is a stub artefact, and hardening the script against it is defensive code for an unreachable condition
- "This test checks only one of its N output lines": an extra line assertion earns its place only when a regression exists that it catches and the suite misses. When the unchecked line comes out of the same code path that another test already pins exactly, and the test's own claim (dedup, sort) is proven by the line count and the checked line, the assertion catches nothing new. Name that regression before accepting (the "deduplicates and sorts invocations across transcripts" test of `commit-transcripts.bats`, walkthrough 2026-09-24)
- Pinning a named non-C locale (`LC_ALL=en_US.UTF-8`) in a `run` wrapper so that a sort-order assertion catches a dropped `LC_ALL=C` on any runner: the suites run as a prek hook on the workstation, whose `en_US.UTF-8` already sorts differently from C, so the detector works where it runs, while a named locale missing on a synced machine makes bash print a `setlocale` warning that `run` merges into `$output` and breaks assertions file-wide. Check the runner's locale before raising it (the "unions the journal and git status" test of `commit-writes.bats`, rejected by L1 and L2, walkthrough 2026-09-25)
- A stub flag called inert because a mode guard excludes its branch. On `word-render.bats` (2026-10-04) the `STUB_LOCKED=1` of the "the pdf route runs on a locked session" test was called non-differential on the ground that `check_session` runs in capture mode only. Measured: the mutant that drops the guard, `[ "$MODE" != "capture" ] || check_session` becoming a bare call, makes that very test fail at its status assertion. Run the guard-dropping mutant before accepting "this flag is inert"; the only mutant such a test misses is one that issues the probe and discards its answer, which no observer of the contract can see
- stdout/stderr separation coverage for `word-render`. Nothing in the repository invokes it outside its own suite and `git log`, and `_meta/notes/docx-verification.md` documents no redirection and no pipe (checked 2026-10-04), so both streams reach the terminal merged and a mutant moving a warning between them is observationally equivalent. A future caller that pipes stdout puts it back in scope, exactly as the `prose-lint` exit-code rule of [[feedback_review_severity_shell_installers]] frames it
- A surviving mutant that is observationally equivalent through the artifact's contract. On `reco-relance.bats` (2026-09-28), dropping `| strings` from the hook's jq filter makes jq abort on a non-string prompt, and the script's `2>/dev/null` plus its trailing `exit 0` turn that abort back into exactly the silence the two tests named for that case assert, so they prove what they claim. Before accepting "this mutant survives", name what an observer of the contract would see differently; nothing means the finding asks for implementation coverage, and the canary remedy offered there (re-running the program extracted from the script, with stderr visible) copies that program into the test file, to resynchronise at every edit. Measured the same day: a jq compile error fails the injection tests and a broken strip regex fails a silence test, so real breakage is already caught (rejected, L1 agreeing)

**A proposed remedy is measured for discriminating power before it is applied, not only the finding.** On `reco-relance.bats` (2026-09-28) the "add a positive counterpart for the `agent-message` strip" finding named a real gap, a greedy-quantifier mutant of the wrapper `gsub` surviving the suite, and its own remedy killed nothing: with a single wrapper, greedy and lazy match the same span, so the proposed fixture duplicated an existing test under another tag. The deciding form was two wrappers of the same tag with the question mark between them, which is also what separates the two `gsub` strips, a `pasted_content` fixture saying nothing about the wrapper alternation. Run the proposed fixture against the mutant it claims to catch, then substitute when it comes back identical. This is [[feedback_probe_must_test_the_deciding_form]] applied to the remedy rather than to the measurement that rules an option out.

**Why:** the `snap-orphans.bats` walkthrough (2026-05-12) rejected 5 of 12 findings under this category. Patterns flagged were valid bats idioms or coverage-for-coverage-sake on bash builtin paths in single-user-workstation context.

**Hermeticity claims about a `_run` helper's env list need measuring, and the list isolates nothing.** The `VAR="${VAR:-}"` entries do not neutralise an exported outer value, they forward it: measured 2026-10-04 on `word-render.bats`, an exported `STUB_LOCKED=1` breaks a capture test that never sets it, although that knob is listed. What the list buys is an explicit passage plus a complete inventory of the knobs, not isolation, and the rig cannot tell a knob set by the test from one set by the shell, both arriving through the same expansion. Accept "add the missing knob to the list" for completeness, never for leak protection. In the same suite a tool missing from `setup()`'s symlink loop also fails loudly rather than silently: dropping `awk` makes 28 of 93 tests fail at exit 127, `pipefail` aborting the script on the `pdfinfo | awk` substitution. Accept that finding for diagnosability (one named setup failure instead of 28 opaque ones) and use `type -P`, never the `command -v` such a finding usually proposes, which returns the bare builtin name for `printf` and would create a broken symlink.

**Env-hygiene findings need their detection direction verified empirically before acceptance.** A finding of the form "`setup()` exports a variable colliding with the script's internal name, which would mask a regression" can be exactly inverted: on `css-toolchain-update.bats` (2026-07-26), the exported `GATE_DIR` is what makes the "reads `CSS_GATE_DIR`, not the hardcoded default" test *fail* under a `GATE_DIR="${GATE_DIR:-…}"` regression, because it points at a directory that does hold a `package.json`. Removing the export creates the masking the finding claims to remove. Inject the hypothesised regression and run the suite both ways before accepting; hygiene alone does not justify losing a detector. The same inversion holds for fixture setup the current implementation no longer reads: in `git-write-guard.bats` (2026-09-27), the `git config alias.*` lines look inert since the guard refuses every subcommand git does not list, but they are what makes a return to alias resolution fail (`alias.st 'status -sb'` turns `git st` into a passing read). Before accepting "this setup changes no result, delete it", ask which superseded design it would catch coming back.

**Assertions whose expected value coincides with the requested input prove nothing about provenance.** A closing report asserting `✓ pkg <the version we just asked for>` cannot distinguish reading the installed tree from echoing the request or the pin. The fix is not to add more packages to the assertion list when their pin, latest, and tree version all coincide too: seed one package's tree version away from *both* its pin and its latest, so any implementation echoing either fails.

**How to apply:** when reviewing `.bats` files for scripts under `~/dotfiles/bin/.local/bin/`, drop the above categories before reporting. Real concerns that remain in scope: tests that pass for the wrong reason (no differential assertion), missing cross-validation, brittle substring matches that would match incidentally, hermeticity gaps (PATH/env leakage, silent symlink-loop degradation, stub writes escaping the sandbox), and bash bugs in the test code itself.

One criterion settles the recurring "this abort path is untested" finding, which arrives undifferentiated and is wrong either way in bulk. A command failing under `set -e` deserves a test only when the failure leaves state that a later guard misreads: until 2026-09-18, `rig-update`'s `setup_apt_repo` fetched a GPG key straight to its destination behind a next-run guard `[[ ! -f "$DEST" ]]`, so a transfer cut mid-flight left a partial key that the guard accepted as installed, which is a missing rollback path and in scope (fixed that day by fetching to a temp file compared with `cmp`; the apt repo and its key were then retired the same day, when `rig-update` moved to the GitHub release `.deb`). A failure with no such state, where the retry is idempotent, gets a test that only asserts that `set -e` aborts, which is a test of bash. Split the finding on that question before accepting or rejecting it. Note also that a stub cannot validate a remedy carried by a flag (a hand-written `curl` stub does not implement `--remove-on-error`, the remedy used then): assert that the script *passes* the flag, which is a differential assertion on the code, rather than that the stub honours it, which is the stub-fidelity trap above.
