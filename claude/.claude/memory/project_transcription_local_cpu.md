Transcribing the user's `.3gpp.3ga` meeting recordings was designed on 2026-09-29 and settled as: `faster-whisper` run ephemerally with `uv` on `ju-TP`'s CPU for the batch, Handy alone for dictation, OpenWhispr not installed, and **no inference delegated to `ju-TP2`'s GPU**. Handy's own dictation settings were decided on 2026-10-02: `cohere-transcribe-03-2026` Q5_K_M on the GGUF `transcribe.cpp` engine, French named explicitly (an `auto` language silently resolves to English on a model reporting `supports_language_detection: false`, which Canary and Cohere both do), `hold_or_toggle` on `ctrl+shift+space`, and `settings_store.json` versioned as the `handy` stow package, whose caveats are in `_meta/notes/dotfiles-bootstrap.md`. **No Canary model transcribes anything on `ju-TP`**: `canary-1b-flash` Q5_K_M and `canary-180m-flash` Q8_0 both return an empty string on every input, on `Vulkan0` and on the `alderlake` CPU backend alike, where `whisper-tiny` on the same engine returns text and `faster-whisper` reads the same clip verbatim, so the fault is the family rather than the engine, the audio or the settings. The Iris Xe beats that CPU backend by 1.8 x, and `transcribe_accelerator: auto` binds it unaided. **A global shortcut cannot work on `ju-TP`'s GNOME Wayland session**: the `tauri` keyboard implementation is `global-hotkey`, which ships an X11 backend and no Wayland one, so its root-window `grab_key` never sees a key pressed in a Wayland-native window, and no typing tool is installed for insertion either. The decision of 2026-10-02 is to log into the Xorg session rather than wire `handy_keys` on evdev plus the `input` group plus `ydotool` on uinput. **One attempt failed silently before the right lever was found**: GDM lists two entries named `Ubuntu`, one per session directory, and resolves that one to Wayland while `WaylandEnable` keeps its default, so `Ubuntu on Xorg` is the only X11 entry, and `AutomaticLoginEnable=true` in `/etc/gdm3/custom.conf` removes the chooser at boot altogether, which is why a pick in the gear menu does not hold. `WaylandEnable=false` is what sticks, set in that file's `[daemon]` section on 2026-10-02 and **in effect since that evening's reboot, under which the whole chain works**: the shortcut reaches Handy, `paste_method: direct` inserts into the focused field through enigo's XTEST path with none of the five typing tools installed, and the user judged the French good over seventeen dictations. `xlsclients` is the diagnostic that distinguishes the two sessions, since both the key grab and the insertion need the focused window to be an X11 client. That file is a dpkg conffile, so a `gdm3` upgrade can drop the key and silently return dictation to Wayland. Managing that file as a stow package was refused the same day: it is a dpkg conffile, root would read it out of a user-writable directory, and a per-machine daemon config does not belong in a replicated repository; a repository-owned file outside `$HOME` goes through a `sudo ln -sf` script, as `stow-rprofile` does. **A silent clip returns a fluent French sentence nobody said**, reproducible through `handy -f` on synthetic digital zeros: 0.5 s gives "Merci.", 1.25 s gives "Sous-titrage Société Radio-Canada", 5 s gives another. A press shorter than `hold_threshold_ms` produces exactly such a clip, because Handy pads a too-short capture to a floor of 20,000 samples (1.25 s at 16 kHz), which is why those phantoms arrive in batches of identical text. The same signature appeared on `faster-whisper` in the batch pass, so it is a family trait with no setting to turn, and the marimba feedback chime that the microphone does capture at the head of every recording is not the cause. Separately, `log_level: debug` wrote every dictated transcript to `~/.local/share/com.pais.handy/logs/handy.log` in cleartext (Handy redacts its own line, then `enigo` logs the same text as `fast_text(text: ...)`), so the level was set to `info` on 2026-10-02 and a dictation then logs none; that log does drop its history (observed once, a relaunch leaving only the new lines, while an earlier launch had appended), by a mechanism left unestablished and plausibly a size-capped rotation keeping one file rather than startup truncation, so the cleartext is not cumulative without bound; `history.db` and `recordings/` keep the last five transcripts and WAVs whatever the level. **Transcription lives in `~/dotfiles/bin/.local/bin/transcribe` since 2026-10-04**, and the `eds-prise/docs/transcript/prise_transcribe.py` prototype that preceded it was deleted the same day, once the tool reproduced its transcript byte for byte from the same recording; `audio.txt` stays as the record of the 2026-09-29 pass, beside the `audio-labelled.{txt,json}` that the tool's first diarized run produced. **The `av>=18,<19` pin is load-bearing**: `av` 19.0.0 (2026-09-29) removed the `metadata_errors` keyword that `faster_whisper.audio.decode_audio()` still passes in 1.2.1, the latest release, so an unbounded `uv run --with faster-whisper` raises `TypeError: open() got an unexpected keyword argument 'metadata_errors'` on any path input; raise both pins together when upstream fixes it. Full reasoning, measurements and rejected ways in `~/dotfiles/.claude/DESIGN-TRANSCRIPTION.md`; do not redo the comparison.

**Why:** the delegation pattern of `~/dotfiles/.claude/DESIGN-GPU-REMOTE.md` (opencode on `ju-TP`, `llama-server` on `ju-TP2`) is the house reflex and will be reproposed by default, but it does not apply here: whisper.cpp publishes no prebuilt CUDA binary for Linux (the Ubuntu release job carries no `GGML_CUDA`, CUDA assets are Windows-only) and `ju-TP2` has no CUDA toolkit, so a GPU path means a toolkit plus a compile or a whole second stack, for a one-off of a few hours of audio. `faster-whisper` also needs no system ffmpeg: its PyAV dependency reads the `3gp` container directly, verified 2026-09-29. Despite the `.3gpp.3ga` extension the recordings are **AAC 48 kHz mono, not AMR-NB 8 kHz**, so there is no narrowband quality ceiling to work around: check the codec before assuming one.

**How to apply:** when dictation misbehaves, check that Handy is running at all before anything else (`autostart_enabled` stays `false` by the user's decision of 2026-10-02, so a reboot leaves no process and the symptom looks exactly like the Wayland failure), then the session type (`XDG_SESSION_TYPE`, `loginctl show-session -p Type`, an `Xorg` process rather than `Xwayland`), and treat a phantom sentence on a short press as the silence artefact above rather than a transcription fault. When transcription comes up again, start from the note rather than from `llama-session`. **Two premises of all this fell on 2026-10-03 and the reco of that day answers them**, so the "no `ju-TP2`" decision and the "no script in `bin/`" rule above are the record of a one-off rather than the current answer: the tool belongs in `~/dotfiles/bin/.local/bin/` so that any project reaches it, and inference crosses to `ju-TP2` over SSH, with the model and the speaker count among the arguments. What the reco settled, against reproposing any of it: `large-v3-turbo` through `faster-whisper` on **both** hosts, a larger model buying nothing measurable on spontaneous French, where the French fine-tunes regress and canary triples the WER; diarization by `pyannote.audio` 4.x with `speaker-diarization-community-1` on **CPU**, in its own process, `num_speakers` being a real constraint there; the payload executed on `ju-TP2` by `ssh` rather than behind an HTTP server; and the `av>=18,<19` pin kept. Neither host needs ffmpeg, pyannote accepting an in-memory waveform, and the GPU ASR path needs no CUDA wheel, reusing the `libcublas.so.12` that `llama-update` already posed in `~/.local/opt/llama.cpp`. **The Hugging Face token that opens the gated `speaker-diarization-community-1` repository lives on `ju-TP2` alone, at `~/.cache/huggingface/token`** (read 2026-10-03, never its content): `huggingface_hub` picks it up with no argument, so nothing needs to pass it, and `ju-TP` has no such file, so any diarization run there fails on the gate until one is placed. **The tool was designed on 2026-10-03 and written on 2026-10-04**: `bin/.local/bin/transcribe`, a bash driver taking `llama-session`'s shapes, over `bin/.local/bin/transcribe-payload.py`, one PEP 723 script run through `uv run --locked --script` with the subcommands `asr` and `diarize`, plus `_meta/tests/transcribe.bats` for the host choice and the refusals. The remote is the default host and an unreachable one refuses rather than falling back, so `--local` is explicit. **Measured on the `eds-prise` recording the day it was written, which also answers "is the GPU hop worth it": 39.81 x realtime on `ju-TP2`'s GPU at `float16` against 5.23 x on `ju-TP`'s 12 CPU threads at `int8`**, 44.42 minutes of audio decoded in 1.1 min against 8.5 min, and diarization adding 20.2 min at 2.20 x realtime on the remote's 24 CPU threads for 883 turns and exactly the 3 speakers asked. The local pass is `cmp`-identical to the 2026-09-29 transcript, which is what retired the prototype. Reach the payload on `ju-TP2` by its synced path, `dotfiles/bin/.local/bin/transcribe-payload.py`, never through a stow link, which a new file of the `bin` package does not get there. **Two measured facts that would otherwise be reproposed wrong.** The reco's two PEP 723 blocks are one: `faster-whisper`, `av>=18,<19`, `pyannote.audio>=4,<5`, `torch` and `torchaudio` from the pytorch-cpu index resolve together on `torch 2.14.1+cpu` with no `nvidia-*` package, CTranslate2 reaching the GPU through llama.cpp's `libcublas.so.12` instead of a wheel. And `[tool.uv.sources]` in a PEP 723 block governs only the **declared** dependencies, so `torchaudio` left transitive arrives as the CUDA build and `import pyannote.audio` dies on `libcudart.so.13`, while a corrected block still reused the cached environment and its wrong wheel until `--reinstall`: `uv run --locked --script` is what closes both, and the `av` pin with them. pyannote CPU diarization runs at **2.27 x realtime** on `ju-TP2`'s 24 threads (10 min in 264.5 s) and the figure is linear in duration (the whole 44.42-minute file at 2.24 x, 1.1 % slower over 4.4 times the audio), `num_speakers` survives `VBxClustering` exactly, and `Pipeline.__call__` returns a `DiarizeOutput` dataclass rather than an `Annotation`, whose `exclusive_speaker_diarization` is the overlap-free field to map segments onto. See [[project_ju_tp2_receiveonly]] for what may never be written on `ju-TP2`.
