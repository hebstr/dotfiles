Transcribing the user's `.3gpp.3ga` meeting recordings was designed on 2026-09-29 and settled as: `faster-whisper` run ephemerally with `uv` on `ju-TP`'s CPU for the batch, Handy alone for dictation, OpenWhispr not installed, and **no inference delegated to `ju-TP2`'s GPU**. Handy's own dictation settings were decided on 2026-10-02: `cohere-transcribe-03-2026` Q5_K_M on the GGUF `transcribe.cpp` engine, French named explicitly (an `auto` language silently resolves to English on a model reporting `supports_language_detection: false`, which Canary and Cohere both do), `hold_or_toggle` on `ctrl+shift+space`, and `settings_store.json` versioned as the `handy` stow package, whose caveats are in `_meta/notes/dotfiles-bootstrap.md`. **No Canary model transcribes anything on `ju-TP`**: `canary-1b-flash` Q5_K_M and `canary-180m-flash` Q8_0 both return an empty string on every input, on `Vulkan0` and on the `alderlake` CPU backend alike, where `whisper-tiny` on the same engine returns text and `faster-whisper` reads the same clip verbatim, so the fault is the family rather than the engine, the audio or the settings. The Iris Xe beats that CPU backend by 1.8 x, and `transcribe_accelerator: auto` binds it unaided. **A global shortcut cannot work on `ju-TP`'s GNOME Wayland session**: the `tauri` keyboard implementation is `global-hotkey`, which ships an X11 backend and no Wayland one, so its root-window `grab_key` never sees a key pressed in a Wayland-native window, and no typing tool is installed for insertion either. The decision of 2026-10-02 is to log into the Xorg session rather than wire `handy_keys` on evdev plus the `input` group plus `ydotool` on uinput. **One attempt failed silently before the right lever was found**: GDM lists two entries named `Ubuntu`, one per session directory, and resolves that one to Wayland while `WaylandEnable` keeps its default, so `Ubuntu on Xorg` is the only X11 entry, and `AutomaticLoginEnable=true` in `/etc/gdm3/custom.conf` removes the chooser at boot altogether, which is why a pick in the gear menu does not hold. `WaylandEnable=false` is what sticks, set in that file's `[daemon]` section on 2026-10-02 and **in effect since that evening's reboot, under which the whole chain works**: the shortcut reaches Handy, `paste_method: direct` inserts into the focused field through enigo's XTEST path with none of the five typing tools installed, and the user judged the French good over seventeen dictations. `xlsclients` is the diagnostic that distinguishes the two sessions, since both the key grab and the insertion need the focused window to be an X11 client. That file is a dpkg conffile, so a `gdm3` upgrade can drop the key and silently return dictation to Wayland. Managing that file as a stow package was refused the same day: it is a dpkg conffile, root would read it out of a user-writable directory, and a per-machine daemon config does not belong in a replicated repository; a repository-owned file outside `$HOME` goes through a `sudo ln -sf` script, as `stow-rprofile` does. **A silent clip returns a fluent French sentence nobody said**, reproducible through `handy -f` on synthetic digital zeros: 0.5 s gives "Merci.", 1.25 s gives "Sous-titrage Société Radio-Canada", 5 s gives another. A press shorter than `hold_threshold_ms` produces exactly such a clip, because Handy pads a too-short capture to a floor of 20,000 samples (1.25 s at 16 kHz), which is why those phantoms arrive in batches of identical text. The same signature appeared on `faster-whisper` in the batch pass, so it is a family trait with no setting to turn, and the marimba feedback chime that the microphone does capture at the head of every recording is not the cause. Separately, `log_level: debug` writes every dictated transcript to `~/.local/share/com.pais.handy/logs/handy.log` in cleartext: Handy redacts its own line, then `enigo` logs the same text as `fast_text(text: ...)`, which matters once clinical content is dictated. Full reasoning, measurements and rejected ways in `~/dotfiles/.claude/DESIGN-TRANSCRIPTION.md`; do not redo the comparison.

**Why:** the delegation pattern of `~/dotfiles/.claude/DESIGN-GPU-REMOTE.md` (opencode on `ju-TP`, `llama-server` on `ju-TP2`) is the house reflex and will be reproposed by default, but it does not apply here: whisper.cpp publishes no prebuilt CUDA binary for Linux (the Ubuntu release job carries no `GGML_CUDA`, CUDA assets are Windows-only) and `ju-TP2` has no CUDA toolkit, so a GPU path means a toolkit plus a compile or a whole second stack, for a one-off of a few hours of audio. `faster-whisper` also needs no system ffmpeg: its PyAV dependency reads the `3gp` container directly, verified 2026-09-29. Despite the `.3gpp.3ga` extension the recordings are **AAC 48 kHz mono, not AMR-NB 8 kHz**, so there is no narrowband quality ceiling to work around: check the codec before assuming one.

**How to apply:** when dictation misbehaves, check the session type first (`XDG_SESSION_TYPE`, `loginctl show-session -p Type`, an `Xorg` process rather than `Xwayland`) and treat a phantom sentence on a short press as the silence artefact above rather than a transcription fault. When transcription comes up again, start from the note rather than from `llama-session`. If the quality disappoints, the next move is a larger model or a `/workflow:reco` on French ASR models, not another topology. If meetings become recurrent rather than one-off, that is when a `bin/transcribe` script with its bats suite earns its place. See [[project_ju_tp2_receiveonly]] for what may never be written on `ju-TP2`.
