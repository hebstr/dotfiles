When reviewing or auditing `SKILL.md` files, or the agent definitions (`agents/*.md`) a skill executes, in `claude-code-plugins/` (and similar Claude Code skill repos), do **not** apply the following patterns from external/cross-model reviewers:

1. **Hypothetical-harness portability hedging.** Findings like "the skill assumes parallel agent calls in one message: might break in a harness that doesn't support that" are not actionable. The skill targets Claude Code, where parallel `Agent` tool calls in one assistant message are a documented, standard pattern (explicit in CLAUDE.md and used by every workflow skill in this repo). Portability to hypothetical reduced-capability MCP harnesses is not a goal.

2. **"My take" / declared-prior framed as anchoring.** When a skill instructs the model to write its prior recommendation before consulting external evidence, external reviewers (esp. Gemini) often flag this as "anchoring bias: synthesize all evidence at once instead." This mischaracterizes the design: the prior is an *audit trail* (declared prior + explicit update), not the final answer. The Final recommendation section is where all-evidence synthesis happens. Reject these findings: the two-pass structure is the safer epistemic shape.

3. **Restating CLAUDE.md global rules inside individual skills.** Findings like "the skill doesn't tell the model to issue a 'starting research now' message before long operations" duplicate a global rule. That example's rule ("Before your first tool call, state in one sentence what you're about to do") is no longer in `CLAUDE.md` or `rules/` (checked 2026-09-22), so it no longer grounds a rejection: first check that the rule the finding would restate is actually loaded. When it is, reject: CLAUDE.md is loaded every session; per-skill restatements drift and bloat.

4. **Explicit-invocation false-negatives.** Every skill in `hebstr/claude-code-plugins` is explicit-only by the user's choice: its description declares "User-invocable only via `/<command>`" (or "Invoke ONLY when the user explicitly types"), and the rule extends to any future skill carrying that sentence. Reject every finding about trigger breadth or narrowness, missing synonyms or FR triggers, oblique requests that never reach the skill, command-typo fuzzy matching, or an auto-trigger fallback: auto-triggering on "rewrite", "walk through", "triage" and their French equivalents opens the skill intrusively all the time, which costs more than a user not knowing the command, and a description reading "any X" is moot because the user types the command. Findings about the skill's internal behaviour (instruction clarity, contradictions, file structure, security, workflow gaps, cross-file coherence) stay valid. The frontmatter flag is not the gate: re-derived 2026-10-10, four `audit/*/SKILL.md` carry `disable-model-invocation: true` (`blindspot`, `walkthrough`, `skill-adversary`, `mcp-adversary`), while `sweep` and every `workflow/*/SKILL.md` do not, so reject a finding proposing to add the flag to a `workflow` skill for alignment, or to remove it from an `audit` one for symmetry. Probe the frontmatter, never the whole file: `rg -c 'disable-model-invocation' sweep/SKILL.md` answers 1 on a body sentence describing `walkthrough`, which is how this rule was briefly miscorrected on 2026-10-10; extract between the first two `---` instead (`awk 'NR==1&&/^---$/{f=1;next} f&&/^---$/{exit} f'`). The flag is also what decides whether a skill reaches the session's own skill list, with no exception over the nine measured that day: the four carrying it are absent from the roster, and `sweep` plus the four `workflow/*` skills, which do not carry it, are all listed. So a redirect target missing from the roster is explained by its flag and is never evidence the redirect is dead.

5. **Part of an utterance read as the whole.** Three shapes, one habit. (a) *Compound criterion*: a completion item joining two clauses ("the files the suggestion touches have been read, **and** the local precedent is named or its absence declared") is not vacuous because one clause is empty in some case; the greenfield case that empties the first leaves the second carrying real work. (b) *Section read without the cross-reference the document itself mandates*: before filing "rule A in section X and rule B in section Y prescribe different outputs for the same case", check whether the document orders the cross-reading. A skill whose intro says "read « When the full framing is disproportionate » before starting" has already linked them, and the discriminator is usually defined in the section the reviewer read in isolation. (c) *Two verbs read as one act*: "the note **is written** after validation" and "**say** in one line which condition holds" govern different acts at different moments; collapsing them manufactures a contradiction and makes a completion criterion look unreachable. Check the verb before filing a timing contradiction.

6. **Trigger or owner restated inside the skill when the global CLAUDE.md already owns it.** Findings like "the skill says decomposition comes first but does not say who executes it" ask the skill to re-document a ceremony CLAUDE.md already specifies end to end (there: "propose decomposition ... User validates before any code is written"). Same family as pattern 3, one level up: not a narration rule but a whole upstream-owned step. Reject; the skill correctly cites the step and stays out of its definition.

7. **Completion-checklist item proposed to restate a section that already carries the rule unambiguously.** Example: "the finished-list has no item on explicit user validation" when a dedicated `Arrêt` / Stop section already defines validation and its negative form. A checklist exists to make the body's requirements checkable, not to duplicate a section that is already imperative. The duplicate drifts on the next edit of either copy.

8. **Specification demanded for behaviour the host or the design already fixes.** Findings that an agent definition "does not specify" a timeout for a background `Agent` (Claude Code always sends a completion notification, failure included), a re-check of an env var mid-session (the Bash tool inherits the environment captured at startup), per-tool availability inside one MCP server (its tools come and go together), a rule combining the verdicts of the main model and its cross-checks (the main model assigns the verdict, the checks are surfaced, the user has the final say), or evidence for a threshold the file already declares uncalibrated. Reject: each asks the prose to re-specify a guarantee it cannot strengthen, or a limitation it already discloses.

9. **Absolute mechanism claim about the audited document's own behaviour, refuted by its literal text or by one command.** Distinct from pattern 5: here the reviewer read the right section and then asserted a behaviour it does not have, usually in a quantifier the whole conclusion rests on. Shapes measured: a verification step described as *executing* code when it only re-reads files, so a revert path is demanded for a failure that cannot occur; a fail-safe declared missing when the file states it twice; a post-filter accused of an assumption the file explicitly declines, with the guard the finding asks for written three lines below; an objection filed as unaddressed when the file already states it, arbitrates it and imposes an anomaly for it; a document header called a fragile self-parse when no serialization boundary exists and three consumers are named; a defense mechanism said to degrade valid high-severity findings "systematically" when it only applies to the band where a cross-check also runs. Read the verb and the quantifier literally, then run the one command that settles the claim, before accepting anything built on it. A finding whose load-bearing sentence is false stays REJECTED even when the mechanism it describes would be a real risk in a document that behaved as claimed; an improvement drawn from it is a separate, voluntary change and is labelled as such, not as acceptance.

10. **A true claim whose only consequence is an action that is correct regardless.** Distinct from pattern 9, where the load-bearing sentence is false: here it holds and decides nothing. Measured on `poc`: the entry check's "a `*-reco.md` note means the pass already ran" does overclaim, the `-reco.md` convention being deliberately shared with the categories the description excludes (three of nine notes on disk are acquisitions, hardware or an OS upgrade), and the clause's single consequence is the action below it, which is right whichever procedure wrote the note: cite it, give its verdict, ask whether the invocation reopens it. Follow an overclaim to the behaviour it governs before accepting it; when the behaviour is unchanged, the wrong reading costs a correction the user sees and makes, while the fix costs a clause that lengthens the rule for nothing.

11. **Duplication between a skill's two eval files read as redundancy.** `evals/evals.json` and `evals/trigger_eval.json` carry overlapping negative-trigger assertions and are not two copies: measured 2026-10-10, `trigger_eval.json` is a flat list of `{query, should_trigger}` that `skill-creator`'s `scripts/run_eval.py` iterates through `--eval-set` and scores mechanically, while `evals.json` is `{skill_name, evals[]}` with an `expected_output` that `skill-creator`'s own `references/schemas.md` defines as "Human-readable description of success", graded by a reader and run by neither harness (`claude plugin eval` reads `case.yaml` or `prompt.md` + `graders/`, not these files). Deleting either side loses something. Two further facts from the same measurement: `run_eval.py` writes a proxy command file whose frontmatter holds only the skill's `description`, so a `trigger_eval` run tests description pull and never the frontmatter gate in either direction; and of the whole marketplace only `audit/blindspot` has ever had a `trigger_eval.json`, so a finding counting three of them is counting files that never existed.

12. **The litrev sub-skill dismissals, migrated 2026-10-13 from the legacy harness store with their subjects re-checked.** They apply to `claude-code-litrev/skills/`, whose five skills are reached only through the `/litrev` orchestrator. No sub-skill has a `README.md` and none is meant to: the `SKILL.md` is the documentation and standalone invocation is unsupported. The `workspace/example-*` directories are internal test fixtures, not pedagogical examples, so their lack of explanatory documentation is not a finding. A long `description` carrying bilingual trigger phrases is the deliberate routing mechanism inside the `litrev-*` family, not bloat. In `litrev-extract`, an authors field arriving as an array in one case and a string in another mirrors upstream variability across data sources, and a `source` field on a semantic claim is required only when abstract and full-text claims are mixed. In `litrev-screen`, the `` !`command` `` form is valid Claude Code dynamic shell expansion, and the `##`-boundary deletion of the `screening_log.md` resume logic is safe because the skill owns that file format end to end; its Step 3 pass-through for articles with no abstract is already documented in the same file. In `litrev-synthesize`, the conditional template sections of `assets/review_template.md` paired with matching `SKILL.md` instructions are the standard mechanism, top-to-bottom execution is the universal skill convention so implicit sequential dependencies are not an ambiguity, and the minimal `allowed-tools: Read Write Edit Bash` is deliberate: adding Glob or Grep to a skill that reads predetermined paths widens the tool surface for nothing. Two items of that legacy list did not migrate: the empty `benchmark.json` / `benchmark.md` carve-out has no subject left (no benchmark file under `skills/`), and the "do not flag packaging polish for litrev-mcp" dismissal is contradicted by the repo's own `.claude/REPO_QUALITY.md`, which now tracks exactly that backlog as open work.

13. **Docstrings on the scripts a personal skill calls.** Do not file documentation-completeness findings on functions in a personal skill's own scripts where the caller is the model guided by `SKILL.md` rather than a human reading signatures: the API contract lives in the `SKILL.md`, and PEP 257 docstrings on every function of a few-hundred-line personal script are boilerplate. Migrated 2026-10-13 from the legacy calibration of the retired `bookmarks-manager` skill; the shape still has a subject, `review-comments/scripts/skeleton.py` carrying no docstring at all. The carve-out stops at the scripts: a missing or incomplete `SKILL.md` is a real finding, and so is a module whose consumer is another script rather than the model.

The patterns come from successive blindspot and walkthrough passes on `workflow/reco`, `design`, the walkthrough's bridge agent, `audit/walkthrough` itself and `poc`. Bucket reliability across these runs is in [[feedback_audit_walkthrough]].

**Lessons beyond the patterns:**

- **Ask of each rule when its trigger becomes observable, not whether its prose is complete.** Every accepted finding of the first `cadrer` pass turned on a condition asked for before it could be observed (a note condition depending on files the reading step never opens, a stop condition unordered against the note step).
- **Re-measure every count and every "nowhere defined" claim.** A reviewer counted twelve `DESIGN-*.md` notes where eleven exist and declared undefined a mapping that `PLAN.md` carries as a table.
- **Where a skill restates a host rule, the remedy is subtraction**: delete the copy and cite the section. The reviewer's default ("restate it faithfully") reopens the drift at the next edit of either copy.
- **On a skill whose script parses a document format, measure every external format claim on the local corpus or the specification before walking it** (the `review-comments` pass, the skill then called `depouiller`: three OOXML claims each failed against files on disk or ECMA-376).
- **Merge a trigger-case block into one point when the skill is explicit-only**: nineteen cases with one cause, rejected by pattern 4, would otherwise have forced nineteen L2 calls.
- **Measure the failure mode a finding asserts**, not only its counts (a claimed exit 127 was an exit 2 the existing branch already surfaced).
- **A rule a skill states in prose usually has an executable twin.** Widening the model-ID regex in `SKILL.md` and the judge left `openrouter-generation.py` and `openrouter-verdict.py` enforcing the old `MODEL_PAT`; when a fix changes a validation rule, grep the scripts the skill calls.
- **Read the project's design note for the skill before adjudicating anything.** `.claude/DESIGN-POC.md` held the seven decisions behind `poc`, its rejected approaches and its open points, and neither source saw it: `skill-adversary` reads only the skill's own directory and the judge receives only `SKILL.md`. Found by accident at point 35 of 39, it corroborated nine verdicts outright and carried two of the errors the audit had just corrected in the skill, so it is at once the fastest ground for a rejection and a second place the same defect hides. Grep `.claude/DESIGN-*.md` for the skill's name first, and correct the note wherever the audit disproves it.
- **Take the cheap wording fix** when L1 and L2 diverge on a one-sentence finding, rather than re-litigating scope.
- **Run the exhaustive coverage check before the wrap-up**: following the report's processing order and then a severity sort once skipped its first critical finding.

**How to apply:** in any future skill-adversary, blindspot, or sweep audit on a `SKILL.md`, skip these thirteen categories of suggestion immediately. Real findings still apply: least-privilege violations in `allowed-tools` (this is exactly the kind of blindspot cross-model review surfaces well), missing failure handling for sub-agents, ambiguous or operationally vague instructions, contradictions across sections, broken tool references after frontmatter changes.
