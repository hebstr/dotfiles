Measured 2026-09-29 on the installed Zotero 10.0.3 (`/usr/lib/zotero/app/omni.ja`), Better BibTeX 9.0.64, the translators in `~/Zotero/translators/`, and the local read-only API.

**PMID and PMCID are native fields now, not Extra lines.** The installed item schema is version 40, and `journalArticle` carries `PMID`, `PMCID` and `citationKey` as real fields, alongside `publisher`, `place`, `section`, `partNumber`, `partTitle`. The schema's own `csl.fields.text` maps `"PMID": ["PMID"]`. `Zotero.Schema.migrateExtraFields()`, called at startup from `zotero.js`, moves recognised `Key: value` lines out of Extra into those fields. So **grepping Extra for `PMID:` finds nothing and proves nothing**: read the field. On this library, 16/16 PubMed-sourced articles and 22/100 sampled articles carry one. Zotero's own support page still lists PMID/PMCID under "Citeable Fields not Included in Zotero"; it is stale, do not cite it. BBT 9.0.64 knows the schema (`"PMID": ["PMID"]` in its build), so Better CSL JSON emits the CSL variable, and `skipFields` cannot reach it (uppercase).

**The connector on a PubMed page and "Add by identifier" with a PMID are one route, not two.** `PubMed.js` declares `"translatorType": 12` (web + search) and both `doWeb` and `doSearch` call `lookupPMIDs()`, which hits the same eutils URL and delegates to `PubMed XML.js`. Identical fields, identical "PubMed entry" link attachment; pick whichever is at hand. The real alternative is PubMed versus the publisher page: PubMed gives the NLM abbreviation, PMID, PMCID and issue but only an OA-resolver PDF, the publisher page gives the PDF directly but an unreliable abbreviation and no PMID. **Do not use PubMed Central when PubMed is available**: same PMID, but the PMC record loses `issue` and `language` (measured on one article, where PubMed also lowercased the full journal title and omitted the URL, so neither identifier route dominates the other — the pre-existing publisher record was the best base of the three). The general rule the incident settled: an identifier route **acquires a missing record, it does not repair an existing one** — re-importing an article already in the library produced three copies that BBT suffixed `a` and `b`, where typing the two missing fields would have cost nothing.

**Only the PubMed route yields a correct NLM journal abbreviation.** `PubMed XML.js` takes `ISOAbbreviation`, falling back to `//MedlineTA`. Everything else is publisher-declared text: `Crossref REST.js` takes `short-container-title` (dropping it only when equal to the full title), `Crossref Unixref XML.js` takes `abbrev_title` with no such guard, `ScienceDirect.js` sets nothing itself and routes through the site's RIS export whose `J2`/`JA`/`JO` tags all land in the same field, and `Embedded Metadata.js` maps `citation_journal_abbrev` unchecked. That last pair is how a record ends up with the *full title* sitting in the abbreviation field, which is worse than empty because it short-circuits every downstream fix.

**Zotero's automatic abbreviation never leaves Zotero.** `extensions.zotero.cite.automaticJournalAbbreviations` defaults to `true`, but its only wiring (`cite.js`) hooks `getAbbreviation` onto citeproc-js. It writes no field and reaches no export. adamsmith confirms it: "Zotero itself doesn't ever use those on export, only in the word processor" (forums.zotero.org/discussion/102230). Its list, `resource/schema/abbreviations.json`, is 2 776 full titles in dotted ISO-4 form plus a 38 077-entry word-by-word engine — not NLM, and missing most mid-tier medical journals.

Three ways out, all partial:
- BBT's `journalAbbreviation` pref (`"abbrev"` default, `"auto"`, `"abbrev+auto"`) — the export worker computes `item.journalAbbreviation || item.autoJournalAbbreviation`, so `abbrev+auto` only arms on an **empty** field and leaves a wrongly-filled one alone.
- `pandoc --citation-abbreviations` (or the `citation-abbreviations` YAML key, which Quarto passes through) — verified working on pandoc 3.12 and overriding `container-title-short`, but exact full-title matching only, and it puts a second source of truth back in the repo.
- Typing the NLM abbreviation from the NLM Catalog. For a small corpus this wins.

**Diagnosing a bad record without opening its source:** `container-title == container-title-short` in the exported CSL-JSON is the exact signature of the abbreviation defect. Inside Zotero, the only published recipe is advanced search with `field — does not contain — %` (`%` alone means "contains anything").

**Zotero has no native metadata re-fetch for an existing item.** The item context menu holds only `Retrieve Metadata` (attachments only) and `Create Parent Item`; the community workaround is re-add by identifier then merge, which requires the same item type. Of the batch plugins, only `northword/zotero-format-metadata` ("Linter for Zotero", v4.0.1, 2026-09-09) is maintained and Zotero 10-compatible, but its abbreviations come from JabRef + LTWA rather than NLM and its update tool only fills *missing* fields. `ZotMeta` stops at Zotero 9; `zotero-shortdoi` and ZotFile are abandoned.

**Why a connector capture of an institutional page has no author or date:** `Embedded Metadata.js` looks for a byline only in the CSS classes `byline`, `bylines`, `vcard`, `article-byline` and gives up otherwise, and it never reads `article:published_time` (its only non-Highwire date fallback is `time[datetime]`). This is structural, not a bug to work around: use the connector for the URL and access date, then type the rest.

**A `.nbib` import is a sound route and lands its PMID natively, which the translator source does not tell you.** `MEDLINEnbib.js` maps `TA` to `journalAbbreviation`, so the abbreviation is the NLM one as with the PubMed route, and its `PMID` branch does `item.extra = "PMID: " + value`, which reads as a defect. It is not, and the chain is `translate_item.js::_saveItem` → `Zotero.Item.prototype.fromJSON`, which sets `migrateExtra = !strict` and so runs non-strict here → `Zotero.Utilities.Internal.extractExtraFields()`, which lifts the recognised `Key: value` lines into their native fields and `setField`s each one. That is the translator-import path, not every save, and it is unrelated to the one-shot startup migration `Zotero.Schema.migrateExtraFields()`, which a `migrateExtra` settings key gates. Measured 2026-10-27 on the nine articles a 2026-10-26 MEDLINE-file import put in the eds-prise library: all nine carry a native `PMID`, an empty `extra` and a correct NLM abbreviation, three of them a native `PMCID` as well. **A reading of a translator's source is not a measurement of the record it produces**, and this one cost a wrong recommendation before the existing nine records settled it.
Choose on volume, not on field quality: the lookup box takes a batch of PMIDs in one paste and needs nothing else, while a `.nbib` costs a round trip to PubMed and buys a single import for records of mixed identifier kinds. Either way the PMCID lands filled and has to be cleared wherever the style is one that prints it. **Whether a PMID has a PMC record at all is one batch call**, no API key and no eutils: `https://pmc.ncbi.nlm.nih.gov/tools/idconv/api/v1/articles/?ids=<comma-separated PMIDs>&format=json`, whose `records[]` entries carry `pmid` and a `pmcid` only where one exists. Measured 2026-11-09 on the 21 PubMed-sourced articles of eds-prise that carried no PMCID: 8 have one, 13 have none, so "fill every PMCID" is never an available option for a bibliography, and an entry without one is information rather than a gap left by the import route.

**One kind of identifier per paste in the lookup box.** `Zotero.Utilities.extractIdentifiers` tries DOI, then ISBN, then arXiv, then ADS bibcode, then PMID, each branch after the first guarded by `if (!identifiers.length)`, so a single DOI in the pasted text silently discards every PMID and arXiv id beside it. Measured 2026-10-27 on the installed Zotero 10 build.

**Volume editors on a conference paper can break an NLM-family style.** Measured 2026-10-27 on `nlm-citation-sequence-superscript.csl`: its `secondary-authors` macro is `<names variable="editor"><label prefix=", "/></names>`, with no suffix and no delimiter, so an item carrying `editor` creators renders `In, éditeursCalzolari N, Kan MY, …` under `lang: fr`, the `In:` losing its colon and the term welding to the first name. An ACL Anthology connector capture brings those editors in uninvited. The page range needs no such care: citeproc collapses and abbreviates it itself, so an en dash in the field prints exactly like a hyphen, and pandoc's `smart` turns a straight apostrophe curly on the way out.

**The PDF route can attach the wrong article, and re-downloading does not fix it.** The `scipdf@ytshen.com` plugin of the profile fetches by DOI from the Sci-Hub static mirror `sci.bban.top`, URL shape `https://sci.bban.top/pdf/<DOI>.pdf#view=FitH`, and keeps that in the attachment's `url`, which is what names the route afterwards. Where the mirror holds a mismatched file for a DOI, every attempt returns the same bytes: measured 2026-11-09 on `10.1016/j.otsr.2020.04.019` (Villatte, shoulder surgery in France), whose file is Casarotti, J. Dairy Sci. 97:6027-6035, md5 `b808c0da73dee19d993af0511f2a7f51` identical before and after deleting the attachment and re-downloading. The notice's own DOI, URL and fields stay correct, so nothing on the Zotero side shows the defect, and the full-text cache then holds the wrong article's text, which makes `rg` over `.zotero-ft-cache` fail in silence. Deleting the attachment leaves its storage folder and file in place until the trash is emptied. The screen that finds such a file without opening any PDF: for each attachment whose `url` matches `bban|sci-hub`, test whether its `.zotero-ft-cache` contains the parent notice's DOI, falling back to a long word of the title. On a 506-attachment library, 91 came from that route and the screen flagged exactly one, so the defect is per-DOI at the mirror and not systemic. It is a screen rather than a proof, a wrong file that happens to carry the string passing it. **Widened to all 332 stored PDFs on 2026-11-09**, scoring four signals off page 1 with a fallback on the extracted cache, the notice's DOI, its first author's surname, its year and the share of title words of six letters or more: 272 pass, 54 are unscorable (a notice whose title is a bare series number, such as a journal-club `LCA 12.`, with no DOI and no creator, which nothing mechanical can match to content), and the six flagged all resolved as correct files. Their false-positive classes are worth knowing before chasing one: a Sci-Hub copy carries an inserted PDFlib PLOP evaluation banner as page 1, a PMC copy of an Elsevier COVID-era article carries the resource-centre notice as page 1, and a notice's singular-plural wording defeats token matching. The one true defect the widened pass found was of another kind, a notice whose only attachment, titled "Texte intégral", is the article's PRISMA checklist appendix. **The identifier route is no escape, and the pref says why**: the plugin writes thirteen Sci-Hub resolvers into `extensions.zotero.findPDFs.resolvers`, every one `automatic: true` and keyed on `{doi}`, scraping `#pdf@src`, which is the pref Zotero's own automatic lookup reads when an item is saved. Measured the same day on the same article: the wand on its PMID created a second notice, which Better BibTeX keyed `villatte2020a`, and the automatic lookup attached the same wrong file from the same mirror. PubMed had nothing else to offer either, `elink` returning only `pubmed_pmc_refs` and no `pubmed_pmc`, so no free full text; and the existing notice already carried the PMID and the NLM abbreviation, so the route would have added no field. The remedy is the publisher page or the institutional access, with the file attached by hand: that lands as `imported_file` with no `url`, which is also what distinguishes it afterwards. A ScienceDirect HTML snapshot already on the notice carries the real text and settles a figure check on its own, but a table's values need `pdftotext -layout` on the table's page, the plain run dropping the numeric column while keeping the row labels.
