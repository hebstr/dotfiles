`word-render` (bash driver plus `word-render-payload.ps1`, `bin` stow package, `_meta/tests/word-render.bats`) renders a `.docx` through the real Word on `ju-TP2`, captures landing in `<project>/.claude/screenshots/`.
Word there is `Word (Unlicensed Product)` and the user has no subscription, so **every write path is shut** (`ExportAsFixedFormat`, `SaveAs2` to PDF and to `.docx`, and `PrintOut` to `Microsoft Print to PDF` all block forever) and the default `pdf` mode refuses on `Application.Caption` in 10 s rather than hanging.
That refusal, and the `-match 'Unlicensed'` guard of the payload, match an English caption while Windows on `ju-TP2` runs `fr-FR` (measured 2026-10-04), so Office's own UI language is what carries them; whether a French Office language pack would silence both and turn the 10 s refusal back into a 240 s wait is untested.
**`word-render --capture` is the route that works**, verified 2026-10-04 on a 9-page deliverable (9 distinct captures, each framed from its top edge to its own footer number, 58 s): Word's layout engine runs fully in reduced functionality, so the line breaking, justification, pagination and colours read from a capture are Word's own. It carries no text layer and it is the screen rendering rather than the print one.

**The one silent failure, measured 2026-10-04:** with the Windows session **locked**, everything reports success. Word opens the file, paginates it and the tool exits 0 with the right page count, but `CopyFromScreen` photographs the lock screen and **every capture comes back pure black**. Read the captures before trusting them: mean luminance 0 against ~0.47 on a legible page, or query the machine for `LogonUI.exe`, which runs only while the session is locked. Since 2026-10-04 `--capture` refuses before triggering the task when `LogonUI` is running, and `LogonUI` is the only reliable signal of the three tried; the `pdf` mode, which never reads the screen, still runs on a locked station. Only the user can unlock `ju-TP2`.

**A station nobody has touched fails like a locked one, measured 2026-10-06.** `--capture` refused three runs with "the window in front belongs to explorer", class `CabinetWClass` then `Shell_TrayWnd`, `SetForegroundWindow` returning `granted=False` each time. No setting had changed: `quser` reported `TEMPS INACT` of `1+16:53`, about 41 h without keyboard or mouse input on the console session, against a display timeout of 300 s on AC and 180 s on DC (`powercfg /q <scheme> SUB_VIDEO VIDEOIDLE`), so the screen had been asleep since the machine was last used by hand. Dark screen, shell owns the foreground and `CopyFromScreen` would read black: the locked-session failure above, reached by another route, and the foreground assertion is what turns it into a refusal instead of black images. **Read `quser`'s idle time first**, before uptime, updates or load: that run had 13 days of uptime, no update since 2026-09-23, CPU at 3 % and 22 GB free. `ForegroundLockTimeout = 200000` is a red herring, 41 h of idleness having expired it long before. Raising `monitor-timeout` afterwards does not help either, a timeout change never waking a display already off, so only a physical wake does. Unverified hypothesis from the same runs: font enumeration went from 27 s to 2 min 21 s on that idle machine, possibly the same dark-screen GDI path.

**Since 2026-10-06 the payload wakes the station instead of needing a hand on it**, in `capture` mode only: a `VK_F15` keystroke through `keybd_event`, then `SetThreadExecutionState(ES_CONTINUOUS | ES_DISPLAY_REQUIRED)` held for the run and released with `ES_CONTINUOUS` in the `finally`. The hold is the half no guard replaces, a display falling asleep mid-run leaving Word in the foreground, so `Assert-Foreground` passes and the captures come back black at exit 0. That refusal now also names the idle time from `GetLastInputInfo`, reliable in the interactive session and useless from the driver's own SSH, which reads the time since boot. **Unverified on a screen actually asleep**: that a synthetic keystroke relights the panel and restores the `SetForegroundWindow` grant is the open assumption, the fallback being the same clean refusal as before. Rejected and not to be re-proposed: a `quser` plus `powercfg` pre-flight refusal in the driver, a luminance probe on a throwaway capture, and a `--wake` flag.

**Why:** the design, every measurement, the three deviations from the written plan (fixed job slot, `Start-ScheduledTask`, the `result.txt` sentinel), the four mechanisms the capture rests on (hide the `NUIDialog` rather than close it, page by `VerticalPercentScrolled` plus `LargeScroll` rather than `ScrollIntoView`, end the instance `Quit` leaves, and `SetProcessDPIAware` with `WdPageFit` 1 for the geometry) and the correction that Aptos *is* available there as a cloud font live in `~/dotfiles/_meta/notes/docx-verification.md`, sections "A fourth route is open" and "The capture route".

**How to apply:** do not re-derive the route or re-propose LibreOffice, ONLYOFFICE, Word for the web or `pandoc --pdf-engine=typst` ([[reference_word_embedded_fonts_blocked]]); run `word-render --capture <file.docx>`. Its refusal names the registration command for the `Claude-WordRender` scheduled task when that task is missing. The page stays white only while `HKCU\...\Word\Options\DisableDarkMode` is `1` on that machine.
