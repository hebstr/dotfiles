`word-render` (bash driver plus `word-render-payload.ps1`, `bin` stow package, `_meta/tests/word-render.bats`) renders a `.docx` through the real Word on `ju-TP2`, captures landing in `<project>/.claude/screenshots/`.
Word there is `Word (Unlicensed Product)` and the user has no subscription, so **every write path is shut** (`ExportAsFixedFormat`, `SaveAs2` to PDF and to `.docx`, and `PrintOut` to `Microsoft Print to PDF` all block forever) and the default `pdf` mode refuses on `Application.Caption` in 10 s rather than hanging.
That refusal, and the `-match 'Unlicensed'` guard of the payload, match an English caption while Windows on `ju-TP2` runs `fr-FR` (measured 2026-10-04), so Office's own UI language is what carries them; whether a French Office language pack would silence both and turn the 10 s refusal back into a 240 s wait is untested.
**`word-render --capture` is the route that works**, verified 2026-10-04 on a 9-page deliverable (9 distinct captures, each framed from its top edge to its own footer number, 58 s): Word's layout engine runs fully in reduced functionality, so the line breaking, justification, pagination and colours read from a capture are Word's own. It carries no text layer and it is the screen rendering rather than the print one.

**The one silent failure, measured 2026-10-04:** with the Windows session **locked**, everything reports success. Word opens the file, paginates it and the tool exits 0 with the right page count, but `CopyFromScreen` photographs the lock screen and **every capture comes back pure black**. Read the captures before trusting them: mean luminance 0 against ~0.47 on a legible page, or query the machine for `LogonUI.exe`, which runs only while the session is locked. Since 2026-10-04 `--capture` refuses before triggering the task when `LogonUI` is running, and `LogonUI` is the only reliable signal of the three tried; the `pdf` mode, which never reads the screen, still runs on a locked station. Only the user can unlock `ju-TP2`.

**A station nobody has touched fails like a locked one, measured 2026-10-06.** `--capture` refused three runs with "the window in front belongs to explorer", class `CabinetWClass` then `Shell_TrayWnd`, `SetForegroundWindow` returning `granted=False` each time. No setting had changed: the screen had simply been asleep since the machine was last used by hand. Dark screen, shell owns the foreground and `CopyFromScreen` would read black: the locked-session failure above, reached by another route, and the foreground assertion is what turns it into a refusal instead of black images. **Read `quser`'s idle time first**, before uptime, updates or load. `ForegroundLockTimeout` is a red herring, and raising `monitor-timeout` afterwards does not help either, a timeout change never waking a display already off, so only a physical wake does. The diagnosis and its numbers are in `_meta/notes/docx-verification.md`.

**Since 2026-10-06 the payload wakes the station instead of needing a hand on it**, in `capture` mode only: a synthetic keystroke, then a display request held for the run and released in the `finally`, the interop detail and the `[convert]::ToUInt32` flag trap being in `_meta/notes/docx-verification.md`. The hold is the half no guard replaces, a display falling asleep mid-run leaving Word in the foreground, so `Assert-Foreground` passes and the captures come back black at exit 0. That refusal now also names the idle time from `GetLastInputInfo`, reliable in the interactive session and useless from the driver's own SSH, which reads the time since boot. **Unverified on a screen actually asleep**: that a synthetic keystroke relights the panel and restores the `SetForegroundWindow` grant is the open assumption, the fallback being the same clean refusal as before. Rejected and not to be re-proposed: a `quser` plus `powercfg` pre-flight refusal in the driver, a luminance probe on a throwaway capture, and a `--wake` flag. The verification was attempted the same day and could not be taken: three runs refused pre-flight on `LogonUI`, the station having locked itself with its screen, confirmed on the panel by the user, so **a dark and unlocked desktop is not reached by waiting here** and the wake waits for a run that lands on that state by itself. Do not propose changing the station's lock policy to force it. **On an unlocked station with its screen lit the whole path runs**, verified the same day on a multi-page report, every capture coming back with a non-zero mean luminance, so the interop compiles and the hold disturbs nothing; only the dark panel stays unverified.

**Why:** the design, every measurement, the three deviations from the written plan (fixed job slot, `Start-ScheduledTask`, the `result.txt` sentinel), the four mechanisms the capture rests on (hide the `NUIDialog` rather than close it, page by `VerticalPercentScrolled` plus `LargeScroll` rather than `ScrollIntoView`, end the instance `Quit` leaves, and `SetProcessDPIAware` with `WdPageFit` 1 for the geometry) and the correction that Aptos *is* available there as a cloud font live in `~/dotfiles/_meta/notes/docx-verification.md`, sections "A fourth route is open" and "The capture route".

**Each run prunes that document's earlier captures, measured 2026-10-07.** A second run announces `replacing N earlier capture(s)` and leaves only the pages it just took, so a `--pages 3-4` control pass after a full one destroys the rest, and `<project>/.claude/screenshots/` is git-ignored with no net. Copy what must survive, or re-take the full range, before narrowing `--pages`; a note citing a capture range goes stale the moment a narrower run lands. The pruning is keyed on the output prefix, so two ranges of one document survive together when each run gets its own `--out-dir` under the screenshots directory (`--out-dir .claude/screenshots/lists`, then `.claude/screenshots/biblio`), which is how two distant page ranges of a 39-page report were captured on 2026-10-24 without re-taking the 34 pages between them. The write check reads `git check-ignore`, so any subdirectory of an ignored `screenshots/` is accepted.

**Past about fifty pages there is no duplicate detection at all, and no remedy exists, measured 2026-10-04 and re-measured 2026-10-12.** `VerticalPercentScrolled` returns an integer percent, 1.64 points per page on a 62-page document, so the payload's duplicate check stands down whenever `100 / (pages - 1)` falls under 2 points. Covering it needs an assertion on the page the pane actually shows, and no API for that is established on `ju-TP2`: `Selection.Information(wdActiveEndPageNumber)` follows the selection rather than the view, and `RangeFromPoint` throws off text. The deliverables this tool serves run 4 to 9 pages, so the blind spot sits outside its normal range; read the captures yourself when a document passes fifty pages. The *skipped*-page half of the same finding is separable, has a derivable remedy and stays an open row of `DEFERRED.md`.

**How to apply:** do not re-derive the route or re-propose LibreOffice, ONLYOFFICE, Word for the web or `pandoc --pdf-engine=typst` ([[reference_word_embedded_fonts_blocked]]); run `word-render --capture <file.docx>`. Its refusal names the registration command for the `Claude-WordRender` scheduled task when that task is missing. The page stays white only while `HKCU\...\Word\Options\DisableDarkMode` is `1` on that machine.
