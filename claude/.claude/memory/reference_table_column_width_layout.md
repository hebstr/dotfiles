Measured 2026-10-06 on gt 1.3.0, flextable 0.10.0 and chromium, in eds-prise.

**Declare one grid in percent and both renderers carry it.** `gt::cols_width()` accepts `gt::pct()` and emits `table-layout: fixed` with one `<col style="width:N%">` per column, the table width falling back to `100%` when nothing declares one; what a memory records as refused is `tbl_format(width = gt::pct(100))`, whose `.check_size()` demands a scalar numeric, not `cols_width()`. For flextable, the share times `hebstr::docx_page_width()` gives the inches of a fixed grid. A percentage is the only declaration independent of the total, so it is what survives a table published at several widths: a report body column, a standalone export, a Word text column. Letting each engine size from content instead gives one table three different grids, which is a defect as soon as the same table is read in two formats.

**The grid divides a total, and the total is declared beside it.** `tab_options(table.width = 700)`, which `hebstr::theme_gt(width = )` reaches, composes with the percentage columns: the table renders `table-layout: fixed; width: 700px` and the `<col>` shares divide those pixels, measured 2026-10-06. Left at `100%` the percentages hold everywhere and the width holds nowhere, the table filling a body column in the report and the whole window in a standalone export, where Word and the PNG stay bounded. So declare both, in pixels at the builder, as `hebstr::tbl_format(width = )` already does for gtsummary and as `tbl_decl()` of eds-prise does at a default of 700; the Word side divides `min(px / 96, docx_page_width())`, which leaves a table wider than the text column exactly where it was.

**`hebstr::easy_out()` rewrites `table.width` only when the `gt` carries `"auto"`**, so a percentage declaration survives the export; `easy_out(width = )` still sets the total and the column percentages follow it. A `gt` left at `auto`, which `width = NULL` gives, is what gets rewritten to `px(700)` on the exported copy, forcing every artifact under `output/` to that width (see [[reference_hebstr_easy_out_subdir]]). That also forecloses the PNG clipping below: at 100 per cent the table cannot exceed the capture viewport, and a declared pixel width is what that viewport is taken from, `width * 1.1`, so the table lands centred with a margin on each side. A **partial** pixel override is the trap: it switches the table to fixed layout, where the undeclared columns keep their content width only while the table width stays auto, and fall to equal shares as soon as anything declares one, which the export path does.

**Word sets the minimum share, not the HTML.** Under a fixed grid a column must hold its widest unbreakable token plus its horizontal indent, and an indentation rule on the first column (`w:ind w:left="300" w:right="100"`, 20 pt) takes that out of its own width where other columns pay 10. Measure the token with `systemfonts::string_width(s, family = "Aptos", size = 9)` and divide by the text column in points: a share one point short breaks every code in mid-token, silently, and only a real-Word readback shows it.

**gt.** With no `cols_width()` the HTML carries neither `table-layout: fixed` nor a `<colgroup>`: the browser's automatic algorithm sizes each column from its content and the table never exceeds its container, shrinking into it instead. Passing any `cols_width()` switches the table to `table-layout: fixed`, but while the table width stays auto the undeclared columns keep exactly the pixels they had with nothing declared, so a partial override pins one column and leaves the rest content-sized. That property dies under `tab_options(table.width = pct(100))`, where the undeclared columns fall to equal shares.

**flextable.** The widths a new flextable is created with are a flat 0.75 inch per column, so a theme that declares neither a grid nor autofit sizes by nothing. `set_table_properties(layout = "autofit", width = 1)`, which `hebstr::theme_ft(width = 1)` reaches, writes `w:tblLayout type="autofit"` with `w:tblW type="pct" w:w="5000"` and **no `w:tblGrid` at all**: Word measures the content itself, indentation and cell margins included, and fills the text column. A per-column `flextable::width()` is then ignored, so there is no partial override on the Word side: covering one column means declaring the whole grid under `layout = "fixed"`. `layout = "autofit"` with no width writes `pct 0`, which sizes to content without filling.

**A declared pixel width scrolls instead of shrinking, and one theme rule fixes it for every table.** `theme_gt(width = )` passes its argument straight to `gt::tab_options(table.width = )` as hard pixels, and `gt` wraps the table in a `width:100%; overflow-x:auto` container, so whenever the body column is narrower than the declared width the table is truncated behind a horizontal scrollbar. The cap below, carried by `quarto-hebstr-doc`'s `theme-base.scss`, makes the declared px behave as a preferred width, kept wherever it fits and compressed below. No `!important` is needed: `max-width` and `width` are different properties, so the cap beats `gt`'s id-scoped `width` rule whatever the specificity. Verified in eds-prise on 2026-09-03, five tables, four viewport widths.

```
table.gt_table {
  max-width: 100%;
}
```

**The capture viewport clips the PNG, and only the PNG.** `easy_out()` captures at `vwidth = width * 1.1`, so a table whose `cols_width()` declares more than the 770 px a 700 px fallback gives loses its rightmost columns in the export with no error raised, the HTML staying correct; a Word render, where `out_qmd()` dispatches a `gt` to `knitr::include_graphics()` of that PNG, is therefore the deliverable that loses them. Measured in eds-prise on 2026-10-03 on a `gt` whose columns summed `500 + 40 × n`: complete at six columns, clipped from seven. A table whose column widths are derived rather than fixed must pass the same sum to `theme_gt(width = )`; `tab_options(table.width = )` normalises a bare integer to `"<n>px"`, so no `gt::px()` wrapper is needed.

**The same overflow on a native `flextable` fails in Word and passes in LibreOffice.** A table given per-column widths through `flextable::width()` under `layout = "fixed"` reaches Word as a `w:tblGrid` of distinct `w:gridCol` values, and it keeps flextable's own default `w:jc w:val="center"`, which `theme_ft()` does not touch. Word honours that grid literally, so a grid wider than the section's text column hangs off **both** sides and the label column's text starts off the left edge of the page: the fills, the spanner and the grid all render, the labels are simply not there. LibreOffice instead scales the grid down to the text column keeping the ratio, so a LibreOffice render reports a pass on exactly this. Measured 2026-10-04 in `R-hebstr/dev/out.qmd` on the same `500 + 40 × n` calendar at fifteen time columns, 16500 twips against a 9360-twip column: 288 px of visible label column predicted, 290 measured, against a correct render once the grid fit. The budget is `docx_page_width()` on the template, 6.3 in (604 px) for `hebstr-doc`, and the fix is a width per renderer rather than one value, the `gt` keeping its HTML pixels. See [[project_word_render_control]] for the route that showed it.

**Before blaming the layout, measure the demand.** Set `table.style.width = "max-content"` in the page and read the columns back: if the total exceeds the container, no width assignment avoids wrapping and the engine is spreading the deficit in proportion to each column's demand. Remove `tfoot` first: the footnote sits in one cell that never wraps, which inflates the whole table's `max-content` past 2000 px and makes `fit-content` useless. A hyphen is a break opportunity, so a short token like `CIM-10` splits across two lines in both engines when its column is minimised; a non-breaking hyphen fixes it for both where a width override would only reach the HTML.

One more sizing fact of the report grid: under `hebstr-doc`'s default the body column equals the viewport minus 541 px, capped at 1002 px (`body-width: 1000px`), so a 950 px table overflows below a 1491 px window and a wide-screen render never reproduces the report.
