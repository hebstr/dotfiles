Serving a GGUF model with `llama-server`, measured in 2026 on three Quadro RTX 6000 (compute capability 7.5, 24 GB each) and on a CPU-only build 9106.

**Two flags defeat the auto-fit and turn a tight fit into a fatal OOM at load.** llama.cpp offloads as many layers as the VRAM allows on its own, and refuses to adjust once the decision is forced. `--n-gpu-layers 99` on a model that does not fit crashes instead of falling back, so that flag is only for *limiting* GPU layers (reserving VRAM for another process). `--tensor-split` has the same effect as a side effect: passing it explicitly disables the auto-fit, llama.cpp detects the overflow and still refuses to adjust. Hence the rule that a small model takes the split and a large one must not: a 70B on 33 GB free crashes with the split and loads with CPU-fallback layers without it. Without the flag at all, everything loads on CUDA0 only. Values are relative ratios, so three identical cards take `1,1,1` and a 24/16/8 GB box takes `3,2,1`.

**`--flash-attn on` needs compute capability ≥ 7.5**, which the Quadro RTX 6000 meets exactly, at the supported floor. It recomputes attention blockwise instead of storing the full matrix, so it cuts VRAM and speeds up long contexts, and it is a pure algorithmic optimisation: identical output, no effect on reproducibility. A CPU backend has no flash-attn implementation and crashes if the flag is left on.

**`temperature=0` alone is no longer guaranteed greedy since PR ggml-org/llama.cpp#9897** ("llama : default sampling changes + greedy update", merged), so `top_k=1` goes in the payload beside it. Under greedy, `seed` has no effect at all. `--mlock` buys nothing when the model fits in VRAM with no swap, and `--numa` only matters on a multi-socket CPU.

**The default thinking mode is the single largest cost on recent models.** Qwen3, Gemma 4 and DeepSeek-R1 chat templates enable it, which added about 1,600 tokens per request on Qwen3.5-27B: 150 s per document against 20 s once disabled by `chat_template_kwargs: {"enable_thinking": False}`. Models without a thinking mode ignore the kwarg silently, with no regression, so it is safe to send unconditionally. One exception measured: `gpt-oss-20b`'s native thinking is not controllable this way and ends in `LengthFinishReasonError`.

**Auto `--parallel` starves each slot.** With `n_parallel = 4` and `kv_unified = true`, the KV budget is shared across concurrent requests, so each slot gets only `ctx_total / 4` (about 3k tokens out of 12,000) and *rejects* a longer prompt. Forcing `--parallel` to the client pool size and sizing `--ctx-size` as context-per-sequence times that number is what guarantees every slot covers the longest prompt. Note that `--ctx-size` is rounded up to align on the slot count (12,000 became 12,032 for 4 × 3,008).

**A hybrid sliding-window plus recurrent-memory architecture cannot reuse the KV cache between requests.** Qwen3.5 and Qwen3.6 combine SWA with Mamba/GDN recurrent memory, and llama.cpp re-processes the whole prompt on every request, logging `forcing full prompt re-processing`. Measured cost on a 5,500-token system prompt: 10-11 t/s against 16-26 t/s for a model without SWA (Ministral-3-14B, Qwen3-30B-A3B). A larger `--batch-size` only cuts the number of prefill passes, it does not restore the cache. Gemma 4 and Llama 3.3 do not have the architecture. Qwen3.8-27B is the same family, 16 Gated-Attention layers over 48 Gated-DeltaNet ones at `head_dim` 256. Upstream tracks this as `ggml-org/llama.cpp` issue 24055, context checkpoints always invalidated on hybrid or recurrent models, open since 2026-06-03 with three fix PRs still open on 2026-11-07: it is a known upstream defect, not a flag to find. `--cache-reuse` is not the remedy, since it does not work with recurrent-state models, and it only keeps the tail of a prefilled sequence after deleting earlier parts while pretending they are still there. A second open defect compounds it on this family, issue 30357: the server's reasoning and content whitespace is not round-trippable through the Qwen3.5-and-later templates, so even a client echoing exactly what the API returned mismatches the cached prefix, measured as 7,260 tokens reprocessed for a prompt 25 tokens longer than the cached one. Strip leading and trailing whitespace from the response client-side.

**`--split-mode layer` is the prefill mode and `tensor` the token-generation mode, so the choice follows the metric and not the card count.** `docs/multi-gpu.md`, byte-identical from b9286 to `master` on 2026-11-07, says `layer` suits a fast prefill and tolerates a slow interconnect, while `tensor` suits fast token generation and only approaches pipeline prefill speeds with a fast interconnect. The author's own benchmark in merged PR 19378, on 2 x RTX 4090 (Ada, not Turing) where NVLink is impossible, on `qwen35 27B`: at pp2048 `layer` 4286.78 against `tensor` 2712.77 tok/s, so 0.63x, and 2486.88 against 2080.78 at depth 65536, so 0.84x; but at the small pp512 at that depth `tensor` wins 1.13x, and tg128 at depth 1.30x. So on PCIe without NVLink, tensor split costs prefill at the large ubatch a real prompt uses and buys decode, and the author's rule is that it favours slow GPUs with a fast interconnect on large dense models at deep context. `-sm tensor` also disables auto-fit, requires flash attention, and refused a quantized KV cache entirely before b9455 (merged PR 23792), which `docs/multi-gpu.md` still does not reflect. When NCCL fails on PCIe, and it does, `GGML_CUDA_ALLREDUCE` takes `internal` or `none` against the Linux default `nccl`.

**Only matched KV quant pairs have a compiled flash-attention kernel, and a mixed pair silently falls back to f16.** `GGML_CUDA_FA_QUANTS` compiles `q4_0-q4_0`, `q8_0-q8_0`, `f16-f16` and `bf16-bf16`, so `-ctk q4_0 -ctv q8_0` converts to f16 at runtime and collapses prefill, measured at about 34 tok/s against roughly 1,000 for `q8_0/q8_0` on a 27B. The silent case became a logged warning only at b10876. On sm_75, prefill is flat within about 1 percent across f16, q8_0 and q4_0, so a quantized KV cache is a VRAM lever rather than a speed one, and it costs decode at depth, around 55 percent of f16 throughput at 64K for q8_0. Separately, `-cram, --cache-ram -1` is documented as no limit but the token cap stays at `n_ctx` while RAM grows about 640 MiB per short prompt on hybrid models: always pass a positive MiB value.

**`--hf-repo` does not reuse a model that `hf` already downloaded.** Build b11065 writes its own cache in the Hugging Face hub layout (`models--<org>--<repo>/{blobs,snapshots,refs}`) under `LLAMA_CACHE`, which defaults to `~/.cache/llama.cpp`, so pointing `LLAMA_CACHE` at `~/.cache/huggingface/hub` looks like it should work. It does not: `hf` and `huggingface-cli` store the blob through **xet**, as `hub/blobs/<2 hex>/<sha256>` reached by a symlink chain from the snapshot, while llama.cpp expects a blob named by its etag inside the repo's own `blobs/`. Measured 2026-10-19 on a 6.3 GB GGUF already present: the server started a fresh download (`<sha>.downloadInProgress`, 56 MB in 35 s) instead of loading it. An orchestrator that hardcodes `--hf-repo` pays the download again, unless it is given a `-m <path>` route to the existing file. A download interrupted partway does resume: the `<sha>.downloadInProgress` files are picked up where they stopped on the next start, measured on a 6.4 GB GGUF cut off at 1.6 GB. Budget for the download separately from any readiness timeout, since a client waiting on `/health` counts the download against it.

**A CPU smoke test does not validate constrained generation.** On build 9106 CPU-only, the free-text path works while grammar-constrained generation with logprobs stalls: prefill completes, then zero tokens in ten minutes on a 0.5B model. The same path was validated on GPU, so the limit is the CPU backend, not the payload.
