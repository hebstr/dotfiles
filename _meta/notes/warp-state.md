# État de Cloudflare WARP sur cette machine

*2026-09-12*

Le client grand public, pas Zero Trust. Il tunnelise tout le trafic et prend la résolution DNS à son compte, ce qui contraint toute configuration réseau posée par-dessus.
Extrait de la note `dns-dnsforge-firefox.md`, où il n'était qu'un obstacle à contourner.

## État mesuré

```bash
warp-cli --accept-tos status
warp-cli --accept-tos settings | head -12
```

```output
Status update: Connected
Always On: true
Switch Locked: false
Mode: Warp
Cloudflare for Families: Off
Disabled for Wifi: false
Disabled for Ethernet: false
Enable DNS logging: false
Exclude mode, with hosts/ips:
  10.0.0.0/8
  100.64.0.0/10
  169.254.0.0/16
  172.16.0.0/12
  192.0.0.0/24
  192.168.0.0/16
```

Les exclusions ne portent que sur les plages privées IPv4, donc le trafic local reste hors tunnel et tout le reste y passe.

Gotcha mesuré : le premier `warp-cli --accept-tos settings` d'une session peut dépasser 120 secondes avant de répondre, puis se comporter normalement ensuite.
Le lancer avec un `timeout` ou en arrière-plan, sinon il passe pour bloqué.

## WARP possède le DNS système

```bash
cat /etc/resolv.conf
resolvectl status | head -6
```

```output
# This file was generated by cloudflare-warp.
nameserver 127.0.2.2
nameserver 127.0.2.3
fd01:db8:1111::2
fd01:db8:1111::3
resolv.conf mode: foreign
```

`systemd-resolved` tourne et reste activé, mais ne sert à rien : WARP écrit `/etc/resolv.conf` lui-même, en fichier ordinaire et non en lien vers le stub, d'où le `resolv.conf mode: foreign`.
Les deux adresses `fd01:db8:1111::2` et `::3` sont portées par `lo`.

Les modes exposés par `warp-cli set-mode` sont `warp`, `doh`, `warp+doh`, `dot`, `warp+dot` et `proxy`.
Aucun ne garde le tunnel tout en laissant le DNS au système.
Le mode « trafic seul, DNS au système » existe chez Cloudflare sous le nom *Traffic only*, mais côté Zero Trust, piloté par le tableau de bord des profils d'appareil et non par `warp-cli`.

**Conséquence pour toute configuration réseau posée ici** : modifier `/etc/resolv.conf` ou `systemd-resolved` à la main pendant que WARP tourne ne sert à rien, le fichier est réécrit.
Un résolveur choisi pour toute la machine impose donc d'abandonner le tunnel, sauf à passer par une application qui fait sa propre résolution, ce que permet le DoH de Firefox.

## Routage par règle, pas par route par défaut

```bash
ip -6 rule show
ip -6 route show table 65743 | head -4
ip -6 route show default
```

```output
32765:	not from all fwmark 0x100cf lookup 65743
::/3      dev CloudflareWARP table 65743
2000::/6  dev CloudflareWARP table 65743
2400::/7  dev CloudflareWARP table 65743
(route par defaut : vide)
```

Tout ce qui ne porte pas la marque de pare-feu `0x100cf`, celle des paquets du tunnel lui-même, part dans la table 65743, laquelle découpe l'espace d'adressage global en préfixes successifs.
Même construction côté IPv4, où la table contient `0.0.0.0/5`, `8.0.0.0/7`, `16.0.0.0/4` et la suite.
La route par défaut de la table principale reste celle du lien physique, `10.139.213.99 dev wlp0s20f3` pour le partage de connexion mobile.

Un `ip -6 route show default` vide est donc la construction attendue et non une anomalie : la règle de priorité 32765 détourne le trafic avant que la table principale soit consultée.
C'est aussi pourquoi lire la seule table principale donne l'impression que rien n'est tunnelisé.

## Étanchéité : pas de fuite IPv6

Contrôlé le 2026-09-12 par `dnscheck.tools`, qui rapporte `104.28.164.251` en IPv4 et `2a09:bac5:322c:28b4::40e:1d` en IPv6, deux plages Cloudflare.

Le mode de défaillance classique d'un tunnel est l'IPv4 qui passe par le VPN pendant que l'IPv6 sort en direct et révèle l'adresse du fournisseur d'accès.
Il ne se produit pas ici : les préfixes `::/3`, `2000::/6`, `2400::/7` et les suivants couvrent l'unicast global, donc les deux familles sont capturées.

L'adresse `2606:4700:110:...` portée par l'interface `CloudflareWARP` n'est pas celle que voient les sites : adresse interne du tunnel d'un côté, sortie de l'autre, deux plages Cloudflare distinctes.

## Géolocalisation et limites

La géolocalisation diverge entre les deux familles, US en IPv4 et Lille en IPv6, parce que les bases ne s'accordent pas sur les plages Cloudflare.
C'est cosmétique, mais avec des effets pratiques : sites servant l'anglais par défaut, contenu géo-restreint capricieux, CAPTCHAs plus fréquents, la réputation de ces plages étant partagée avec beaucoup de monde.

Nuance de fond : l'IPv6 géolocalise à Lille, donc WARP ne déplace pas, il choisit une sortie proche.
L'adresse réelle est masquée aux sites visités, la ville reste inférable, et Cloudflare connaît l'origine.
Pour un besoin d'anonymat plutôt que de chiffrement du transport, WARP n'est pas l'outil.

~~~
