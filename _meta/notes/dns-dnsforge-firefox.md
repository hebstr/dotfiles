# Résolveur DNS dnsforge.de : DoH dans Firefox (option A)

*2026-09-12*

## Contexte

`dnsforge.de` est un résolveur DNS public allemand (opérateur Giebel.IT / adminforge.de, PowerDNS, serveurs en Allemagne, gratuit sur dons) qui filtre publicité, traqueurs et malware au niveau de la résolution de noms.
Annonces de l'opérateur : DNSSEC validant, aucun log de requêtes, DoT / DoH / DoQ, limite de 100 requêtes par 10 secondes.
Le « no logging » est une déclaration, non vérifiable de l'extérieur.

Quatre profils, chacun avec ses IP, son nom DoT et son point d'entrée DoH :

| Profil | Pub + traqueurs + malware | Jeunesse (adulte, jeux d'argent) | DoH |
|---|---|---|---|
| Normal | oui | non | `https://dnsforge.de/dns-query` |
| Clean | oui | oui, plus SafeSearch forcé | `https://clean.dnsforge.de/dns-query` |
| Hard | listes strictes, aucune whitelist | non | `https://hard.dnsforge.de/dns-query` |
| Blank | aucun filtre | non | `https://blank.dnsforge.de/dns-query` |

La documentation du site ne couvre ni Linux ni les routeurs : les guides fournis sont Android, iOS, Firefox, Chrome, Edge.

## Contraintes de la machine

Deux éléments décident du choix de la méthode.

**Cloudflare WARP possède le DNS système.** `/etc/resolv.conf` est généré par `cloudflare-warp` et pointe sur `127.0.2.2`, le client tourne en `Always On: true`, `Mode: Warp`, et aucun mode du client grand public ne garde le tunnel en laissant le DNS au système.
Toute résolution système part donc chez Cloudflare, et modifier `/etc/resolv.conf` ou `systemd-resolved` à la main pendant que WARP tourne ne sert à rien, le fichier est réécrit.
Un résolveur choisi pour toute la machine impose d'abandonner le tunnel, sauf à passer par une application qui fait sa propre résolution, ce qu'offre le DoH de Firefox.
Détail de l'état du tunnel, des modes disponibles et du routage dans `warp-state.md`.

**Pas de box, connexion par forfait mobile via point relais.** Rien à configurer au niveau réseau local, et le lien peut être instable.
C'est ce qui écarte le mode « Protection maximale » de Firefox (voir ci-dessous).

## Option A appliquée : DoH dans Firefox

Firefox garde son propre résolveur DoH, indépendant du DNS système. C'est donc la seule méthode qui cohabite avec WARP sans rien démonter.
Portée : Firefox uniquement. Chromium, `apt`, `curl`, R, Python continuent de passer par WARP.

Prefs ajoutées au `user.js` du profil :

~~~js
user_pref("network.trr.mode", 3);
user_pref("network.trr.uri", "https://clean.dnsforge.de/dns-query");
user_pref("network.trr.custom_uri", "https://clean.dnsforge.de/dns-query");
~~~

Profil Clean depuis le 2026-09-12, Normal auparavant.
`custom_uri` ne sert qu'à afficher l'adresse dans le panneau Paramètres, `uri` est celle qui est utilisée.

**Le mode 3 est obligatoire ici, et c'est le résultat contre-intuitif de cette note.**

Quatre prefs posées pendant le diagnostic ont été retirées après vérification dans la source qu'aucune n'a d'effet :
`request_timeout_ms` ne gouverne pas ce mode, `GetRequestTimeout()` renvoyant `network.trr.request_timeout_mode_trronly_ms` quand le mode vaut TRR-only, soit 30000 ms par défaut ;
`confirmationNS` est redondant, le mode TRR-only posant `CONFIRM_DISABLED` avant même que le `skip` soit testé ;
`max-fails` n'est lu nulle part en pratique, `RecordTRRStatus` sortant avant de compter dès que `network.trr.retry_on_recoverable_errors` est vrai, ce qui est sa valeur par défaut ;
`doh-rollout.disable-heuristics` est redondant, le contrôleur se désactivant seul dès qu'un mode est posé à la main.

**Retirer une ligne de `user.js` ne supprime pas la pref.** Elle reste inscrite dans `prefs.js` à sa dernière valeur et continue de s'appliquer.
Le retrait complet suppose de supprimer aussi la ligne dans `prefs.js`, Firefox fermé, ou de la réinitialiser depuis `about:config`.
Fait pour les quatre, et vérifié durable : Firefox a réécrit `prefs.js` à la sortie de la session suivante sans les réintroduire.

Contrepartie assumée du mode 3 : aucun repli. Si dnsforge devient injoignable, plus rien ne se résout dans Firefox, et l'attente peut durer trente secondes avant l'échec.
Le retour au mode 2 ne coûte qu'une ligne, mais il rétablit l'absence totale de filtrage décrite plus bas.

### Pourquoi le mode 2 ne filtre rien

Constaté le 2026-09-12 : en profil Clean, les sites pour adultes s'affichaient normalement dans Firefox.
La configuration était pourtant juste, `clean.dnsforge.de` présent dans `user.js` comme dans `prefs.js`, et le résolveur bloquait bien, en A comme en AAAA :

```output
                Normal            Clean
pornhub.com     66.254.114.41     0.0.0.0   (AAAA : ::)
bet365.com      5.226.179.10      0.0.0.0   (AAAA : ::)
example.com     104.20.23.154     172.66.147.243
```

Deux mesures côté client cadrent le problème : `network.trr.mode` vaut bien 2 en valeur utilisateur dans `about:config`, et la colonne `TRR` d'`about:networking#dns` est à `false` sur un domaine ordinaire.
Firefox avait donc la configuration et ne s'en servait pas.

**La cause : Firefox lit une réponse de blocage comme une panne du résolveur.**
Le passage en mode 3 le dit explicitement. Les sites ordinaires se chargent, donc la connexion DoH fonctionne, et `bet365.com` donne la page d'erreur TRR de Firefox, intitulée « Hum, nous ne parvenons pas à trouver ce site », avec pour motif « Un problème est survenu avec clean.dnsforge.de ».
Une réponse `0.0.0.0` n'est donc pas traitée comme une adresse, mais comme un défaut imputé au fournisseur DoH.

D'où le comportement des deux modes, qui n'a rien d'un réglage mal choisi :

- en mode 2, chaque domaine bloqué ressemble à une défaillance, Firefox se rabat sur le DNS système, le domaine se résout normalement et **le filtrage est structurellement impossible**
- en mode 3, il n'y a pas de repli, l'échec reste un échec et le blocage tient

C'est aussi ce qui explique les deux familles de résolveurs relevées dans `dnscheck.tools` au début de l'installation.

**Conclusion pratique : sur un résolveur filtrant par réponse nulle, le mode 2 ne filtre pas.** Le choix n'est pas entre robustesse et filtrage, il est entre pas de filtrage du tout et le mode 3.

Trois explications ont été avancées et invalidées avant celle-ci : le verrou `max-fails`, la limite de débit partagée avec les autres sorties WARP, et le verrou de confirmation.
Le `network.trr.confirmationNS` à `skip` posé à ce titre est resté sans effet, ce qui se comprend rétrospectivement : la confirmation n'était pas l'obstacle.
Le `mode=0` lu dans les logs de démarrage est l'état d'avant lecture des prefs, `ModeFromPrefs` dans `TRRServiceBase.cpp` se contentant de lire `network.trr.mode`.

**Hypothèses éliminées par mesure**, à ne pas reprendre :

- le fichier de configuration, correct et appliqué, `prefs.js` portant les mêmes valeurs que `user.js`
- le résolveur, qui bloque en A, en AAAA et en HTTPS RR de type 65
- `network.trr.fallback-on-zero-response`, à `false` par défaut, donc pas de contournement du `0.0.0.0`
- les heuristiques de déploiement DoH, que `DoHController` désactive dès que `network.trr.mode` ou `network.trr.uri` porte une valeur utilisateur, en passant l'état à `manuallyDisabled`
- le suffixe `.` que WARP inscrit via `search .` dans `/etc/resolv.conf` et que Firefox ajoute à sa liste de suffixes : `IsExcludedFromTRR_unlocked` compare des sous-chaînes exactes après chaque point, donc `bet365.com` produit `bet365.com` puis `com`, jamais `.`
- le verrou `max-fails`, qui existe mais n'était pas en cause
- le transport, HTTP/3 et QUIC à travers le tunnel WARP compris : le mode 3 charge les pages normalement, donc la connexion DoH s'établit sans difficulté

**Méthode de diagnostic**, réutilisable :

~~~bash
MOZ_LOG='sync,timestamp,nsHostResolver:5' MOZ_LOG_FILE=/tmp/trr.log firefox <url>
~~~

Le `sync` est obligatoire, sans lui le fichier est créé et reste vide.
Le module s'appelle `nsHostResolver` et couvre aussi le service TRR.
Le fichier contient un octet nul, donc `rg` le prend pour un binaire : lui passer `-a`.

Limite qui a rendu cette méthode inutile ici, et qui vaut d'être connue avant de la retenter : **Firefox résout les noms dans son processus socket**, pas dans le processus parent.
Le log parent ne contient que les rares résolutions du parent, en pratique `incoming.telemetry.mozilla.org`, que Firefox marque délibérément `TRR_DISABLED`, ce qui produit un `TRR service not enabled` trompeur.
Les fichiers `child-*.moz_log` sont restés vides.
Pour capturer les résolutions de pages, il faudrait d'abord basculer `network.process.enabled` à `false` afin que le DNS revienne dans le parent.

Ce qui a tranché n'est pas le log mais une sonde : poser le mode 3 et regarder si les pages se chargent.

**Contrôle** : `about:networking#dns`, colonne `TRR` sur la ligne d'un domaine ordinaire.
La ligne du résolveur lui-même, `clean.dnsforge.de`, est toujours à `false` et ne prouve rien : Firefox ne peut pas résoudre l'adresse de son propre résolveur DoH par ce résolveur.

### Le fichier est stow-managé

Paquet `firefox`, créé pour l'occasion :

~~~
~/dotfiles/firefox/.mozilla/firefox/z24d9fn6.default-release/user.js
~~~

Posé par `cd ~/dotfiles && stow firefox`, le profil existant étant un répertoire réel déjà peuplé, stow ne replie donc pas l'arborescence et ne lie que le seul fichier.
C'est le comportement voulu : le répertoire de profil contient `places.sqlite`, `cookies.sqlite` et le cache, il ne doit jamais être stowé en entier.
Le `lock` visible à côté du lien est un symlink créé par Firefox à l'exécution, pas un artefact de stow.

Le lien est sûr parce que **Firefox lit `user.js` et ne l'écrit jamais** : il n'écrit que `prefs.js`.
Vérifié par les mtimes, `user.js` figé à 13:35 pendant que `prefs.js` était réécrit à 13:51 au cours de la même session.

Sur une machine où ce répertoire de profil n'existe pas encore, un `stow firefox` nu se comporterait autrement : stow replie les arborescences dont la cible est absente et lierait `~/.mozilla` lui-même vers le dépôt, ce qui y ferait atterrir le profil Firefox entier.
D'où le `stow -R --no-folding -t ~ firefox` isolé dans le bootstrap du README.
Comportement documenté de stow, non mesuré ici.

Fragilité assumée : `z24d9fn6` est un nom généré à la création du profil.
Une réinstallation ou une réinitialisation de Firefox produit un autre nom, le lien pointe alors dans le vide et le réglage disparaît sans message d'erreur.
C'est le seul paquet dotfiles lié à une machine précise.

### Changer de profil dnsforge

Éditer le chemin réel sous `~/dotfiles`, jamais le symlink, puis fermer et relancer Firefox.
Les deux lignes à modifier sont `network.trr.uri` et `network.trr.custom_uri`, avec l'URI voulue dans le tableau des profils plus haut.
Le changement ne prend pas effet à chaud.

### Piège du user.js

Les valeurs de `user.js` sont réappliquées à chaque démarrage de Firefox.
Un changement fait dans l'interface ou dans `about:config` tient jusqu'à la fermeture, puis revient à la valeur du fichier.
Pour piloter le réglage depuis l'interface, retirer du fichier dans le paquet ses trois lignes `network.trr`, puis relancer Firefox.
Les valeurs déjà écrites dans `prefs.js` restent en place, l'interface reprend la main à partir de là.
Ne pas passer par `stow -D firefox` pour cela : cela retire le lien entier, donc aussi `browser.profiles.enabled` qui n'a rien à voir avec le DNS.

Note sur l'interface : la section DNS peut être introuvable dans Paramètres > Vie privée et sécurité selon la version.
La boîte « Rechercher dans les paramètres » en haut de la fenêtre, avec `DNS`, la retrouve quelle que soit la disposition.
Aucune `policies.json` d'entreprise n'est présente sur cette machine, rien ne masque donc la section.

## Vérification

Firefox étant fermé au moment de l'édition, le réglage prend effet au prochain lancement.
Trois contrôles, du plus rapide au plus complet :

1. `about:networking#dns` : la colonne `TRR` doit afficher `true` sur les entrées récentes
2. ouvrir <https://dnsforge.de> et regarder l'encart de test de la page
3. <https://dnscheck.tools/> ou <https://browserleaks.com/dns> : des résolveurs Hetzner en `ptr: dnsforge.de` doivent apparaître. Voir plus bas pourquoi des résolveurs Cloudflare peuvent figurer à côté sans que ce soit un défaut

Contrôle du filtrage lui-même : une page chargée d'habitude de publicité doit venir sans.

### Résultat mesuré, 2026-09-12

Deux passes, qui valent autant par leur différence que par leur contenu.

**En mode 2**, `dnscheck.tools` remontait quatre résolveurs Hetzner en `ptr: dnsforge.de`, soit les adresses du profil Normal alors en service, **et deux résolveurs Cloudflare à Paris**.
Deux lectures successives ont été données de ces deux lignes et toutes deux étaient fausses : un artefact de la rafale de sous-domaines du test, puis un verrou de confirmation qui n'aboutissait pas.
L'explication est celle de la section « Pourquoi le mode 2 ne filtre rien » : chaque domaine bloqué étant lu comme une panne, une part des résolutions repartait en DNS natif.

**En mode 3**, refait le même jour après nettoyage des prefs : plus aucune ligne Cloudflare dans « Your DNS resolvers ».
Quatre résolveurs Hetzner à Falkenstein, `49.12.43.208`, `49.12.223.2`, `2a01:4f8:c17:4fbc::2` et `2a01:4f8:c012:ed89::208`, tous en `ptr: clean.dnsforge.de`, donc les adresses du profil Clean et non plus celles de Normal.
C'est la confirmation que toute la résolution du navigateur passe par dnsforge et que le profil en service est bien le bon.

DNSSEC dans les deux passes : PASS sur les quatre lignes (signature valide, invalide, expirée, absente) pour ECDSA P-256, ECDSA P-384 et Ed25519, donc validation effective.
Piège de lecture : sur les lignes « invalide », « expirée » et « absente », PASS signifie que le résolveur a correctement refusé de répondre.

Ce test est le contrôle de référence : la présence d'une ligne Cloudflare y signale un chemin de résolution qui échappe à TRR.

### Adresses IP

Les adresses affichées en haut de `dnscheck.tools` ne disent rien du DNS, elles décrivent la sortie du tunnel WARP.
Contrôlées le même jour, rien à corriger, notamment aucune fuite IPv6.
Analyse dans `warp-state.md`.

### Si un site casse

Le blocage est décidé par les listes tierces, pas par l'opérateur. Pour identifier le domaine fautif :
F12 > onglet Console > F5, puis chercher les erreurs rouges du type `net::ERR_NAME_NOT_RESOLVED`.
Le domaine trouvé se signale via la fonction whitelist de la section Blocklisten du site.

## Option B, préparée mais non appliquée

Filtrage sur toute la machine via `systemd-resolved` en DoT.
Exige d'abandonner le tunnel WARP, donc de perdre le masquage d'adresse IP. À trancher seulement si l'option A convainc après usage réel.

Étapes, dans l'ordre :

~~~bash
warp-cli --accept-tos disconnect
sudo mkdir -p /etc/systemd/resolved.conf.d
sudo tee /etc/systemd/resolved.conf.d/dnsforge.conf >/dev/null <<'EOF'
[Resolve]
DNS=176.9.93.198#dnsforge.de 49.12.67.122#dnsforge.de
DNSOverTLS=yes
DNSSEC=allow-downgrade
Domains=~.
EOF
sudo ln -sf /run/systemd/resolve/stub-resolv.conf /etc/resolv.conf
sudo systemctl restart systemd-resolved
resolvectl status | head -12
~~~

Points d'attention :

- le `#dnsforge.de` après l'IP est le nom attendu dans le certificat TLS, il est obligatoire en DoT
- `/etc/resolv.conf` est actuellement un fichier ordinaire écrit par WARP, pas un lien : le `ln -sf` le remplace, donc en garder une copie avant
- retour arrière : supprimer le fichier `.conf`, `warp-cli --accept-tos connect`, redémarrer `systemd-resolved`
- `resolvectl query` et `resolvectl statistics` servent au diagnostic

## Option C écartée

Configuration au niveau du routeur : sans objet, il n'y a pas de box. Le point relais mobile n'expose pas de réglage DNS.
